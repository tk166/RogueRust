### The answer to "how many bytes after pre-compiling"

* `out/content.rdcf` -- complete, exact content image: **180936 B (176.7 KiB)**
* `out/content.core.rdcf` -- same minus presentation: **144004 B (140.6 KiB)**

Against the ESP32-P4 budget of 592 KiB of usable SRAM: the full image is
30% of SRAM, the core image 24%.  Neither has to live in SRAM at all.
The image is read-only and immutable, so it belongs in flash (or memory-mapped
PSRAM), with SRAM holding only the interpreter's registers and node cursor.

## 3. What stopped being stored, and why that is safe

Nothing is *dropped* from `content.rdcf` -- `validate.py` proves the round trip
is structurally exact.  What disappears is **redundancy**:

The one deliberate exception is the **document keys** (`DOC_ROOT_KEYS`): they are build
metadata, not game data, so they are written into neither image and are therefore *not*
part of the round trip (`Rom.document()` reproduces the source minus those keys).

| redundancy | compact JSON bytes it occupies | how the binary avoids it |
|---|---|---|
| object key names (50544 occurrences, 233 distinct) | 550793 | an opcode's field descriptors spell each key once, not per occurrence |
| `{"kind":..,"value":..}` discriminant envelope | 192261 | the opcode *is* the kind |
| redundant `Children` second copies | 0 | subtree interning: a repeated child is one u16 handle |
| byte-identical program bodies | 0 | the same interning |
| id wrapper objects (`{"value":s}` / `{"Value":s}`) | 41530 | the field's flags byte carries the spelling; the object is never stored |

These rows overlap: the envelope row is the literal serialised bytes of
`"kind":<K>,"value":` at each of the IR nodes, and its two key names are
already counted in the key-name row.  They are listed separately because they
are eliminated by different mechanisms.

Sources of truth for each of those claims:

* **`Children`** is `ConditionalEffectNode.Children`, a read-only computed
  property (`Effects/Programs/EffectProgramNodes.cs:65,85-87`) that the
  deserialiser ignores; `CombatJson.cs:166-193` already prunes it when it is not
  a constructor parameter, and the comment there records the incident that made
  them do it: one boss rule reached 311,624 nodes / 15 MB while the tree itself
  held about 40 nodes.  **RDCF keeps it regardless** -- interning makes it cost
  almost nothing, and keeping it makes the round trip exact instead of an argued
  equivalence.  Only the *copies* vanish, worth 0 B of compact JSON.
* **Key names / the envelope** are not inferred from a schema: the compiler
  observes the union of fields actually present per (kind, object-shape) and
  emits a descriptor.  A field whose observed storage classes cannot be
  reconciled falls back to `F_JSON` (canonical text, still exact):
  **0 field(s) needed that fallback**.
* **Id wrappers.**  `CombatIds.cs:3-78` declares 16 `readonly record struct`
  ids.  The document spells the same id bare, as `{"value":s}` (3,128 refs) or
  as `{"Value":s}` (747 refs).  A field that is uniform in spelling stores just
  the string id and remembers the wrapper in its flags byte; only a genuinely
  mixed field spends a term.
* **Presentation** is not dropped by default.  `content.core.rdcf` is a second
  build with exactly this list removed, which is the entire difference between
  the two images:

  * `Cards[]`: `NameKey`, `DescriptionKey`
  * `Encounters[]`: `HeroDisplayName`
  * `EnemyActions[]`: `NameKey`, `DescriptionKey`
  * `Relics[]`: `DisplayName`
  * `Statuses[]`: `NameKey`, `DescriptionKey`
  * `EnemyActions[].Intent.Label`
  * `Encounters[].Enemies[].DisplayName`
  * `Events[].situations[].TextKey`, `...Choices[].TextKey`, `Shops[].Offers[].TextKey`
  * the whole `Presentation` object (4 B compact)

  Measured effect: compact 995099 -> 929036 B; binary 180936 -> 144004 B (saves 36932 B, 20.4%).

subtrees, so peak usage stays near the cost of the parse itself.

## 6. Determinism

`validate.py` builds the image twice in one process and compares SHA-256.  Every
ordering decision is explicit:

* fields within an opcode: sorted by name
* object shapes: sorted by key tuple; IR kinds: sorted by kind string
* string pool: sorted by UTF-8 bytes, so ids are stable regardless of traversal
* terms: insertion order over a sorted-key walk
* id symbol table: sorted by (string id, entity kind)

`content_hash` in the header is FNV-1a-32 of the raw source file, so a stale
image is detectable without re-parsing.

## 7. What this report does *not* prove

`compile.py` measures.  Correctness is `validate.py`'s job, and it writes
`out/validate.md` (full image) and `out/validate-core.md` (stripped image).
Those reports check, independently of anything here:

* well-formedness -- every section aligned, disjoint and in range
* a **structural round trip**: `reader.py`'s reconstruction compared against
  `json.loads(source)` per path, including key *presence*
* reference integrity -- every cross-entity id resolved, every dangling one
  listed with its site
* ASCII-only ids, byte-identical rebuilds, id-namespace hygiene, and how much
  of the image the map cannot reach

Both images currently pass every check.
