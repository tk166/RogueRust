# RogueRust 第十四轮增量审查：P2 WASM–UI 集成

> **版本范围**：`472b500cca6620d594cd04583621cf786ce2e8bb^..8383837adea99551bff510404d8137ef9da62e5e`  
> **审查基线**：终点提交 `8383837`；代码与文档永久链接均锁定此 SHA。  
> **重点**：P2 分层、真实 WASM 动作、输入状态机、快照/Beat、场景布局与门禁。  
> **证据范围**：基于公开 GitHub 的提交页面、终点版本源码及 `docs/ui-p2-adapter.md` 进行静态交叉审查。没有获得完整 Git compare 补丁，也未在本地安装依赖、构建 WASM、运行浏览器或真机。文中将“源码可证实”“可推导风险”“尚需动态验证”分开。  
> **刻意不做**：不借此评审触发 V2 内核重构、不扩大 MCU 预算要求、不把 P3 以后的整局 UI 工作误判成 P2 必须完成。

## 0. 决策摘要

**P2 的主干架构是成立的，可以继续沿用**：`WasmHost` → `decodeCombat` → `GameStore` → `CombatView` → `Stage/HUD/Overlay`。这是真正的浏览器 WASM 战斗集成，而非 Mock 伪装；第 28 门将 ABI 探针与 3D 视图分离、第 29 门验证操作后真实 DOM 跟随内核、第 27 门验证纯逻辑，均值得继续保留。

**建议先闭环 3 个最实质的 P1，再进入大规模 P3 界面开发**：

1. **无目标卡的 Action 枚举与 UI 目标语义混淆**（两端源码可证实）；
2. **正在拖动的 Action 索引缺少状态版本校验**（错误执行风险，需构造交叉操作复现）；

另应补上 ABI 哈希的运行时比对和拒绝操作不变量的显式错误处理，并纠正以文案猜卡牌类别的临时代码；这几项可以边完善 P2 边进入 P3 小范围开发，不需要重新设计分层。

## 1. 已经做对的工程设计

### 1.1 ABI 单一接入点 + 纯解码

- `web-next/src/wasm/host.ts` 是直接读 `instance.exports` 的边界。把 `_len/_into` 的参数顺序留在调用点，用闭包封装 `readText()`，避免对所有导出强行套一个参数次序。
- `web-next/src/wasm/snapshot.ts` 不接触 WASM，能用模拟 `Int32Array` 对敌人空槽 `-1`、战斗结果、X 费 `-2` 与动作种类单独测试。
- `web-next/src/wasm/store.ts` 统一 `dispatch()`，可用于记录 before/after、只在被接受时交付 Beat，避免 R3F 组件直接修改规则状态。
- `web-next/src/view/combatView.ts` 保留 `viewFromMock`/`viewFromWasm` 两个生产者，统一渲染组件，不再重写 R3F 布局。

**可沉淀规范**：ABI 变化必须同时检查 `host` + `snapshot` + `store` + `view` + ABI 探针，不允许某一层静默填充貌似合理的默认值。

### 1.2 实际浏览器门禁，优于只检查 Mock

- `native/ui_wasm_check.mjs`（第 28 门）在不画 3D 的探针中验证观察解码、Action、拒绝操作的可观察不变性。
- `native/ui_wasm_ui_check.mjs`（第 29 门）检验 UI 拖牌后实际敌人血量、手牌和能量改变，并检查 DOM 的血量字符串跟随新状态。
- 单独的中文翻译映射与未翻译回退计数，避免用英文 ID 伪装中文内容已完成。
- `docs/ui-p2-adapter.md` 主动列出 X 费端到端尚未触发，这比泛称全部 P2 已通过可靠。

**限制**：当前真实浏览器覆盖的是固定种子、固定战斗路线，不代表全部卡牌语义、所有 Pending、所有目标选择与真实手机手感。覆盖矩阵的结论不应大于实际执行断言。

## 2. P1-A：无目标卡牌在 UI 中被误认为定向牌（确定问题）

**位置**：

- [Rust compute_actions L1674–1756](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/kernel/rd-wasm/src/lib.rs#L1674-L1756)
- [combatView.ts L98–115, L141–151](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/view/combatView.ts#L98-L115)
- [pointerMachine.ts L61–80](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/input/pointerMachine.ts#L61-L80)

**证据**：Rust 明确表述当前无法廉价区分“是否真的需要目标”，所以 **每张可出的牌都为每个存活敌人生成一条 `ACTION_PLAY`**，对非定向卡牌附带一个敌人槽位不会影响内核规则。而视图用 `actions.some(targetSlot >= 0)` 推定 `targeted`，状态机用 `options.some(slot >= 0)` 推定 `needsTarget()`。

**反例**：`Defend` 有两名敌人时，Action 表可能包含 `(Defend, enemy0)`、`(Defend, enemy1)`，但在 StS 意义上它不需要敌人目标。新 UI 将要求点敌人或拖到敌人才能使用，空白处释放则回弹，还可能错误提示攻击目标。

**正确原则**：**动作枚举的 `targetSlot` 不是卡牌的目标声明**，不能将它当作 `TargetingMode` 的唯一事实来源。

**最小修复方案**：

1. 从内容包的确定性卡牌元数据建立 `CardTargeting`（`none | singleEnemy | other`，`other` 不臆断）；若内容编译器确无可靠声明，可增加一个极小的只读元数据 API，不要用规则文字/颜色猜。
2. `CombatView` 用 `targetingMode` 决定视觉反馈；`optionsFor` 依然只绑定内核真正枚举的 `actionIndex`。
3. 对 `none` 类型，把所有内核过度指定的 Action 归并为一个**规范代表动作**：即使 `targetSlot >= 0`，UI 业务上仍显示无目标；释放后从原动作列表中选一条有效 Action。不要虚构 `targetSlot=-1` 的内核条目。
4. 对 `singleEnemy`，要求命中合法敌人；对 `other` 先通过单独模态/机制处理，不强行套敌人拾取。
5. 添加 **两敌人 Defend：空白处释放仍获得格挡** 与 **Strike：空白处不能提交、拖到指定敌人才造成伤害** 两条真实浏览器测试。至少再验证一次“无目标多动作候选执行等价性”。

```ts
// 设计示意：业务语义与动作索引分离；不是可直接覆盖仓库的完整补丁。
type CardTargeting = 'none' | 'singleEnemy' | 'other';
interface CardPlayIntent {
  handSlot: number;
  targeting: CardTargeting;
  legalActions: readonly CombatAction[];
}
// none 的代表 Action 取自 legalActions（不是手工构造），
// singleEnemy 必须按 targetSlot 精确匹配。
```

## 3. P1-B：拖拽中的动作表可能过期，数字索引不能独立作为身份（高置信度风险）

**位置**：

- [pointerMachine.ts L24–45](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/input/pointerMachine.ts#L24-L45)：按下时冻结 `DropOption`，只持有 `actionIndex` 和手牌槽位。
- [App.tsx L213–260](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/App.tsx#L213-L260)：松手后按 `index` 从**当前**动作表再次寻找，不比较 kind/handSlot/targetSlot，也无版本标识。
- [App.tsx L492–509](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/App.tsx#L492-L509)：回合结束按钮可独立发起 `GameStore.dispatch`。

**问题**：Action 列表位置可能在牌组、能量、角色死亡、待决选牌等状态变化后重新分配。用户按下时 `index=3` 指的是“槽位 0 的 Strike 打敌人 1”；在松手前若另一个操作令状态改变（例如结束回合、选择/使用药水），新 Action 表的 `index=3` 可能是不同卡牌或不同敌人。`find(a => a.index === result.actionIndex)` 仍会命中，于是**过期的用户手势执行另一条当前合法动作**。

这是静态可推导的保护缺口；**是否已能通过当前界面操作时序触发，仍需专门的组合浏览器测试**，不能说已观察到误出牌。

**最小修复**：

- `GameStore` 维护 `epoch`（所有会改变 Action 表的提交都要递增，包括战斗动作、选牌确认、药水使用等）；开始手势时同时冻结 `epoch` 与业务卡牌/目标信息。
- 释放时先比较 `epoch`，不一致就取消当前手势；再对照当前 `CombatAction` 的 `(index, kind, handSlot, targetSlot)`，不可只比 `index`。
- 要彻底避免“同一槽位、同定义的新实体”误认，则后续需要稳定 `CardInstanceId` 或专用不可变操作 token；第一阶段可以用 epoch + 当前动作四元组先闭环。
- 产生 Pending Choice、结束回合或刷新场景时，主动 `dismiss` 当前拖拽，防止显示卡牌和规则状态脱节。

**建议测试**：按住卡 A → 通过回合结束/药水等另一条路径改变 Action 表 → 松开；期望不会出卡 B，且有明确取消反馈。

## 4. P1-C：横屏 `n=4` 违反原定每行最多 3 个敌人的约束（确定问题）

**位置**：[formation.ts L69–105](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/stage/formation.ts#L69-L105)。

§360 改成：

```ts
const singleRow = n <= 4;
const upperCount = singleRow ? n : Math.ceil(n / 2);
```

这个修正解决了 `n=2` 的 `1+1` 在一条竖线上叠放的问题，但**引入 `n=4` 的单排 4 名**。用户早期明确的需求是“横屏自动排布成两行，每行 1–3 个敌人”，因此该公式与需求不符。§360 文档中“用户要求 n≤4 一排”的表述也不是该原始约束的准确转述。

更符合原意的布局表：

| n | 横屏排布 | 竖屏排布 |
|---:|---|---|
| 1 | 1 | 单列 1 |
| 2 | 单排 2（而不是上下各 1） | 单列 2 |
| 3 | 单排 3 | 单列 3 |
| 4 | **2+2**（或明确选 3+1） | 单列 4 |
| 5 | 3+2 | 单列 5 |
| 6 | 3+3 | 单列 6 |

> 这里“允许用一排”是针对少量敌人避免视觉退化，并不是允许一排超过 3 名。

**建议测试不变量**：对所有 n=1..6，横屏每排人数 <=3、非空行数<=2、敌人 slot 不丢不重、位置互不重叠；再加 `n=2` 水平分开、`n=4` 恰好两排、`n=5` 3+2。不要让测试只照抄新公式，否则容易再次把错误规则固化为绿色断言。

## 5. P1-D：拒绝操作“未改变状态”的反馈超出了实际检查能力（确定接口缺口）

**位置**：[store.ts L69–102](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/wasm/store.ts#L69-L102)；[App.tsx L231–254](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/App.tsx#L231-L254)。

`GameStore.dispatch()` 对前后两份 **148 格观察向量**做逐项对比，记录 `unchanged`。这证明“可观察向量不变”，并不能证明随机数、内部实例、Pending 细节或其它未导出的内核状态全部未改变，**不要把它描述成整个状态逐字节不变**。

而 `App` 只依据 `outcome.accepted` 显示反馈。只要不是 accepted，一律说“内核拒绝了这一步 · 状态未改变”，完全**没有检查 `outcome.unchanged`**；即使观测向量真的变化，也仍然会给出不实的安慰信息。`STEP_BROKEN`、`STEP_FINISHED` 与普通拒绝也被揉成同一句。

建议：

```ts
if (outcome.code === STEP_REJECTED && !outcome.unchanged) {
  // 契约级错误：记录快照、冻结进一步操作并展示诊断。
  throw new Error('ABI violation: rejected action modified observation');
}
// rejected 且 observation 未变：显示“动作被拒绝”。
// broken：显示驱动错误，不把它当普通玩家操作失败。
// finished：显示终局语义，不显示“状态未改变”。
```

后续若需要验证**完整内核失败原子性**，应使用 Rust 自身的 full hash / state 对比测试，而不是由 UI 观察向量替代。

**建议门禁负控**：Mock Host 返回 `-1` 却篡改一个观测字段，要求 Adapter/界面显式失败，不得显示普通“未改变”。

## 6. P2-A：WASM 文件哈希目前只是“记录”，不是运行时“比对”（确定问题）

**位置**：

- [host.ts L141–152](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/wasm/host.ts#L141-L152)
- [host.ts L479–522](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/wasm/host.ts#L479-L522)
- [sync-wasm.mjs L33–56](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/scripts/sync-wasm.mjs#L33-L56)
- [package.json L5–10](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/package.json#L5-L10)

构建脚本生成 `wasm.json`，包含 WASM 的 SHA-256，并在注释中承诺“装载时比对”。**实际 `WasmHost.load()` 计算哈希后只放进诊断对象，并未读取预期 manifest SHA 作运行时比较。** `validate()` 也没有接收预期 SHA。第 28 门确实把公共 manifest 与 `web/rd_wasm.wasm` 核对了，但这不等于任意生产部署都做运行时完整性检查。尤其 `npm run dev` 只执行 `vite`，没有自动同步 WASM，开发环境可能载入旧副本。

**最小修复**：`load()` 同源取得 manifest 后比对 `sha256 === manifest.sha256`，再校验内容指纹/ABI 版本；对网络缓存设一致部署策略。另可在 `dev` 前执行 `sync-wasm`，或将 dev 模式做成显式“当前 WASM 未同步”的报错，而不是静默使用旧副本。

现有“同一构建产物”的 CI 方案是合理的，**这里只建议补齐运行时语义，不要求引入第二套构建链**。

## 7. P2-B：卡牌类型按描述文本猜测，正式 UI 会显示错误卡面（确定设计债）

**位置**：[combatView.ts L75–85](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/view/combatView.ts#L75-L85)。

```ts
return /damage|伤害/i.test(rules) ? 'attack' : 'skill';
```

判断“描述中包含伤害”不等于“卡牌是 Attack”：某些 Skill/Power 也涉及伤害，某些 Attack 的文字可能不含固定关键词，Power 一律无法正确显示。虽然目前用于配色，但 StS 类型颜色会影响玩家快速识别与选择，属于 UX 数据正确性问题。

**修复方向**：按内容定义的 `CardKind` 构建元数据索引，按定义 ID 或 `defSlot` 显式查表；不要用中文文案、英文文案或正则表达式推断游戏事实。可和 §2 的 `TargetingMode` 元数据一起输出，避免重复做一套规则解释器。

## 8. P2-C：按手牌位置构造 ID，不是卡牌实例身份（未来集成风险）

**位置**：[combatView.ts L98–115](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/view/combatView.ts#L98-L115)。

`id: hand-${slot}-${defSlot}` 在手牌压实时改变同一张卡的前端身份；新卡重新占用相同槽位时也会复用旧 ID。对于 3D 卡牌进入/退出/移动动画，这会导致视觉对象错误复用或重建。`CardInstanceId` 后续应来自引擎的稳定实例标识（若 ABI 当前没有，不可自造假身份）。

**P2 的短期做法**：按槽位映射一次性布局，不承诺跨状态实体连续性；用 `epoch` 避免跨状态拖动；到需要“同一张卡从抽牌堆入手、出牌、弃牌”的连续动画时，再评估最小实例 ID 导出。

## 9. P2-D：敌人溢出被内核报告，但新 UI 没有消费该报警

Rust 提供 `rd_env_enemy_overflow()`：当真实敌人超过 6 个、观察向量无法表达时返回 1。`WasmHost.REQUIRED_EXPORTS`、`snapshot()`、`GameStore` 当前都未读取它。`decodeCombat` 只比较截断后的 header 与六个槽位数，两者会一致，不能捕获被截掉的敌人。

**最小修复**：在 `WasmHost.snapshot()` 进入解码前读取 overflow；发现 1 时拒绝显示“全部敌人已可操作”，转为显式诊断或后续扩容处理。未证明当前合法遭遇必然超过 6 名，暂列 P2 边界防御。

证据：[Rust L1488–1508, L2341–2352](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/kernel/rd-wasm/src/lib.rs#L2341-L2352)、[host.ts L29–91](https://github.com/tk166/RogueRust/blob/8383837adea99551bff510404d8137ef9da62e5e/web-next/src/wasm/host.ts#L29-L91)。

## 10. P2-E：待决选牌的显示限制可以更严谨

`ChoiceModal` 只检查 `selectedCount >= min` 来决定是否允许确认，未同时检查 `selectedCount <= max`。超上限时内核确实会拒绝并给出提示，功能上不至于无声失效，但前端应先阻止明显无效的确认，并在多选上限时禁用未选选项。 `ChoiceModal.tsx` 文件头说明仍写 kind 只有三种，实际 `choiceText.ts` 已支持十种，注释过期。

这属于局部 UX 与文档修整，不是需要重构整个 Pending 机制的信号。

## 11. P2 与 P3 的边界：当前是“真实战斗演示”，还不是完整整局新 UI

- `App.tsx` 默认用固定 seed 自动开局、遍历地图并进入战斗。这是 P2 的 deterministic fixture，**不能被理解为已有地图/商店/事件完整可交互 UI**。
- `GameStore.dispatch()` 已提供战斗 Action 回调；主页面仍未形成从胜利到 `fight_end`、奖励、地图等整个 Run 状态的交互闭环。
- Beat 目前主要被 `describeBeats()` 转成提示文案，不等于序列化演出队列、分镜、跳过动画和速度控制均已实现。
- X 费的展示/解码已有覆盖，但真实 X 费扣能量与选目标等行为仍需要定向夹具。

这些是**明确的下一阶段项目范围**，不应记为本轮 P2“违规缺失”，也不要为了它们先写庞大通用框架。

| 优先 | 改动 | 必须让测试证明的性质 |
|---|---|---|
| **P1** | 区分 Action 目标枚举与卡牌实际目标语义 | 两敌人 Defend 在空白处可使用；Strike 空白释放不提交；都取真实合法 Action |
| **P1** | 手势冻结状态版本与动作四元组 | 按下后另一路改变内核状态，松开不会执行被重新编号的动作 |
| **P1** | 拒绝返回码与 `unchanged` 联动 | `rejected && !unchanged` 必须触发契约错误；broken 不显示为普通拒绝 |
| P2 | 比对 wasm manifest SHA | 修改 wasm 但保留旧 manifest，装载必须拒绝 |
| P2 | 从内容元数据读取 kind/target mode | 非攻击型伤害描述不误绘为 Attack，Power 正确显示 |
| P2 | 消费敌人 overflow 报警 | >6 时显式报告而不是悄悄少显示敌人 |
| P2 | Choice 上限和文案校验 | 超出 max 时按钮/选项受限，10 种 kind 显示有界 |
| P3 | 真正的整局 UI 状态切换 | 开局→地图→房间→战斗→结算→奖励→地图；与 Rust 权威状态一致 |

### 负控建议

- 故意给无目标牌注入两个敌人 Action，测试必须仍把它判作 `targeting:none`；
- 手势开始后改变 Action 表的顺序，测试必须拒绝旧 index；
- 让 Host 返回 `STEP_REJECTED` 但篡改观察向量，测试必须响亮失败；
- 在 4 敌人阵型时强行塞第 4 名进同一排，布局门禁必须红；
- runtime manifest 中改一个 SHA 字符，加载必须失败。

**这些测试应该区分纯状态机、Adapter、真实浏览器三个层级**。对错误预期做负控时不要直接修改正式工作目录；使用临时 worktree 或只修改测试注入的替身对象。

## 13. 本轮最值得沉淀的原则

1. **状态事实、动作合法性、交互意图是三种不同语义**。Action 表枚举合法转移，但未必描述“玩家应该怎么选目标”。
2. **数值索引不是实体身份，也不是跨快照的动作身份**。应当用权威版本边界控制手势提交；稳定实例 ID 按真实演出需求增加。
3. **失败可观察不变 ≠ 完整内核状态不变**，而且“检测到不变性异常”必须在 UI 中显式失败，不可仅记录后照样报成功。
4. **测试要从用户已声明的不变量出发**：每排至多 3 名，不能因为修复 n=2 的竖直退化就把 n=4 的单排 4 名当成正确行为。
5. **先做一场正确的真实战斗，再做整局 UI**。P2 架构已经足以支撑 P3，不需要现在重新设计 Rust Core。

## B. 一处需要强调的根因

审阅把 P1-A 的原因写成一句话，我认为这是本轮最值得沉淀的：

> **动作枚举的 `targetSlot` 不是卡牌的目标声明。**

内核**故意**为每张可出的牌 × 每个活敌人各发一条动作（`env-lib.rs` 注释明说"过度指定目标是无害的"，
因为它无法廉价判断"这张牌是不是定向牌"）。UI 拿 `some(targetSlot >= 0)` 去反推"要不要目标"，
就把内核的**枚举策略**当成了**卡牌语义**。修法必须从内容元数据取"要不要目标"，
动作表只用来取 `actionIndex`。

## C. 处置顺序（已确认）

1. **P1-A + P2-B**：从内容包生成 `id → {kind, targeting}` 元数据表，一次解决"要不要目标"与"什么种类"；
   对 `none` 的牌把内核过度枚举的多条动作**归并成一个代表动作**（不虚构 `targetSlot=-1` 的内核条目）；
   带两条真实浏览器负控：**两敌人时防御空白释放要生效**、**打击空白释放必须回弹**。
2. **P1-D + P2-A**：`rejected && !unchanged` ⇒ 契约级错误响亮失败；`broken`/`finished` 分开说；
   `load()` 真读 `wasm.json` 比对 sha，`dev` 未同步就报错。
3. **P2-D + P2-E**：消费 `enemy_overflow`；ChoiceModal 查上限 + 修过期注释。
4. **P1-B**：`GameStore` 维护 `epoch`，手势冻结 `(epoch, index, kind, handSlot, targetSlot)`，
   松手时四元组不匹配就取消（需要多指时序的构造测试）。
5. **P1-C**：横屏 `n ≤ 3` 单排、n=4 → 2+2，回到"每行 ≤ 3"。

## D. 对审阅两处措辞的保留

1. **"拒绝 = 一个字节都不改"** —— 审阅指出这超出实际检查能力，**接受**。本项目 §纪律 8 原文
   要求的是"整个结构体相等"，但 wasm 侧只有 148 格向量可读；因此措辞统一改成
   **"可观察向量逐字节不变"**，并在 `store.ts` 注释里写明它**不覆盖**随机数与未导出字段。
   完整的失败原子性应由 Rust 侧的 full-hash 测试保证（已有 `hash_full`），不由 UI 代替。
2. **P1-C 的"用户早期明确需求"** —— 我确认这是真实存在的原始约束（"每行 1–3"），
   §360 的实现与文档确实把它改掉了，**接受审阅意见**，按更强约束回退。
