# RougeRust 项目架构与开发实践评审

> 本稿由网页端评审整理。复制时标题、表格和代码围栏丢失，已按仓库现状重排。
> 对照范围：`docs/port-plan.md` 至 §159，以及文中点名的源码。未在本机重跑测试；文中的通过数来自开发日志，不作为独立验收。

## 总体结论

架构方向是对的，工程验证方法也明显好于一般个人游戏项目。目前最值得改的不是性能，而是状态一致性、内容扩展能力、测试有效性和开发流程。

按第一阶段目标：

- 保留现有 Rust Core + Run + WASM + Web UI 分层，不做整体重构。
- 暂时停止围绕 MCU 内存做额外设计。堆分配、动态容器和更便利的内部结构可以用。
- 先解决规则扩展时的正确性，避免每加一张卡、一瓶药、一件遗物都可能弄坏已有流程。
- 从逐个补物品，转到机制级开发：先把一类机制做完整，再批量挂内容。

## 一、当前到了什么程度

`port-plan.md` 现为 10,339 行、159 节。原评审停在 §158；§159 已落地 Ascension 框架和开局种子，数字以此为准。

| 项 | 记录值 | 说明 |
|---|---|---|
| 单元测试 | 757 | §159.8：rd-core 631、rd-run 80、rd-wasm 46。§158 时为 752 |
| 验收闸门 | 18/18 | 最近一次日志记录，未经本机复跑 |
| 幕数 | 3 | 整局结构已有 |
| 卡牌定义 | 30 | 含升级行，不是 30 张独立基础卡 |
| 敌人 / 遭遇 | 31 / 22 | 当前内容包 |
| 药水 / 遗物 | 20 / 13 | 药水目标 33，遗物远未到清单规模 |
| 状态 | 24 | §158 起未再改内容镜像 |

数据流值得保留：

```text
Web UI（HTML / CSS / JS）
    输入、页面、展示、动画
        │  Action / Observation
        ▼
rd-wasm
    Session、内容读取、战斗与整局协调
        │
        ├── rd-core   战斗执行、效果程序、状态、意图、确定性 RNG
        └── rd-run    地图、房间、奖励、商店、牌组、遗物、整局状态
                │
                ▼
        Content Compiler + RDCF
            声明式配置 → 编译 → 运行时读取
```

`rd-run` 不直接依赖具体内容，`rd-core` 只管规则执行，前端通过 ABI 操作状态而不是复制规则。这三条约定不要拆。

## 二、已经做对的事情

| 实践 | 评价 | 理由 |
|---|---|---|
| 战斗核心与整局分离 | 优秀 | 生命周期和状态所有权清楚 |
| RDCF 内容编译 | 保留 | 内容与执行分离，能做静态校验 |
| C# Oracle 差分 | 优秀 | 不靠直觉重写战斗语义 |
| 固定种子与状态哈希 | 优秀 | 可复现、可对拍、可回归 |
| Web UI 纯函数描述层 | 优秀 | 显示语义可以单独测 |
| CDP 浏览器测试与随机 Soak | 方向对 | 能抓到纯 Rust 测试看不到的交互问题 |
| 分层验收闸门 | 有用，但不够 | 闸门数量不等于行为覆盖 |

§50、§150–155 的方法是对的：某个测试抓不到真实错误时，先复现假阴性，再补有针对性的自动化。§158.5 又证明了这一点：一次编辑吞掉 `#[test]`，测试仍能编译、跑零次、闸门不红。§159.1 已经对 Ascension 用了「阈值前一档 / 阈值本身」双侧断言，说明边界测试不是新发明，只是还没铺到所有分段规则上。

## 三、源码复核后仍然成立的问题

以下四条都在当前树上核对过，不是泛泛建议。

### P0. 商店购买不是原子的

`kernel/rd-run/src/state.rs` 的 `buy_card`（约 1976 行）和 `buy_relic`（约 2001 行）都是先扣钱，再 `push_*`：

```rust
self.adjust_gold(-offer.price);
self.push_card(offer.id.as_str())?;
self.shop.cards[slot].price = -1;
```

`push_card` / `push_relic` 在容量满时返回 `RunError::Capacity`（`MAX_RUN_DECK = 60`）。此时金币已经扣掉，货架也还在。调用方看到 `Err`，可观察状态却已变。

`remove_card` 和 `take_card` 不是同一形状：前者校验完再改牌组，后者先 `push_card?` 再清奖励。不要把「商店」整段都当成坏的，坏的是「先提交、后可能失败」。

契约应是：拒绝的操作不改变可观察状态，必要时包括 RNG。简单操作先校验再写入；多步操作用临时副本或提交点。不必上事务框架。

优先补的回归：牌组或遗物栏已满时购买，断言 `Err` 且购买前后状态指纹一致。故意把扣钱挪回 `push` 之前，测试必须变红。

### P1. 运行层内容池仍会静默截断

同文件 `MAX_POOL = 64`。`pick_potion`（约 1846 行）、`pick_relic_avoiding`（约 1923 行）、`roll_reward` 的卡池过滤（约 2415 行）都是 `take(MAX_POOL)` 或 `len().min(MAX_POOL)`。超出的条目不进抽样，也不报错。

这和 §158 刚修过的形状相同：当时 `MAX_POOL_IDS = 8` 把药水表截成前 8 项。那次的修法是删掉按幕分池、直接读 `POT` 全表，并在内容门里拒绝超长的遭遇/事件池。遭遇和事件池现在是**响亮失败**；药水、遗物、奖励卡池仍是**静默截断**。

当前 20 瓶药、13 件遗物、30 条卡定义都碰不到 64。第一阶段不必为了省字节留着它。要么改成按输入长度分配，要么保留数组但在遍历前拒绝超限。拒绝必须进内容门或单测，不能只写注释。

### P1. Eternal Feather 的整数顺序是错的

`rest_heal_per_cards`（约 1598 行）：

```rust
bonus += amount * i32::from(self.deck_len) / 5;
```

规则是每 5 张牌 3 点，应先整除再乘：

```rust
bonus += amount * (i32::from(self.deck_len) / 5);
```

`amount = 3` 时：

| 牌组 | 应恢复 | 现实现 `(3 * n) / 5` |
|---:|---:|---:|
| 5 | 3 | 3 |
| 8 | 3 | 4 |
| 9 | 3 | 5 |
| 10 | 6 | 6 |
| 14 | 6 | 8 |

§157 的 `the_new_relics_pay_out` 用了 10 张牌，两种写法都是 6，所以全绿。这不是测试数量不够，是分段函数只测了整档。

### P1. Eternal Feather 的触发时机和稀有度也错了

数值错误之外，绑定的生命周期就是错的。

`docs/spec/sts-act1-inventory.md` 写的是：进入休息点时，每 5 张牌回复 3 HP，稀有度为 Uncommon。因此选 Smith 也应吃到这次治疗。

当前实现把这笔治疗加进 `rest_heal()`，而 `rest_heal()` 只在 `rest()` 里调用。`smith()` 只换牌、清 `Pending::Rest`，不治疗。§157 的表还把它写成 Rare，内容 `sts.roguedeck.json` 的 `Rarity` 也是 `Rare`。掉落池按这格抽，所以这不是显示文本问题。

应拆成两个事件，而不是改一个公式：

- 进入休息点：Eternal Feather。
- 选择休息：30% 治疗和 Regal Pillow。

同表还有一件同类归类错误，原评审没写到：`golden_idol` 在清单里是 event-only，内容里却是 Rare，而 `relic_pool` 会把整张 `REL` 表送进商店、宝箱和精英奖励。效果函数可以留，稀有度和掉落资格要跟清单对齐。

## 四、开发方法

### 1. 从「测试够多」改成「测试抓得到」

除上面的具体缺陷外，这是最值得先做的流程改动。

`tools/acceptance.ps1` 的 clippy 闸门只要求退出成功且输出含 `Finished`，没有 `-D warnings`。§158.5 那种「测试还在、属性没了、总数仍过门槛」因此还能再出现。绝对路径也还在：`acceptance.ps1` 写死了本机 Python、Cargo，`tools/cargo.ps1` 写死了 Rustup。个人脚本能跑，但不能当可复制的验收入口。工具链应从 PATH 或环境变量发现，再逐步进 CI。

建议四层，不要再加一道只数行数的闸门：

| 层 | 方式 | 目的 |
|---|---|---|
| L1 | 单测、表驱动 | 每条规则算对 |
| L2 | 性质测试 | 大量输入上不变量成立 |
| L3 | 差分、固定种子回放 | 改规则不悄悄改旧语义 |
| L4 | 浏览器 E2E、随机 Soak | 玩家实际操作能走完 |

L1、L3、L4 已有基础。最缺 L2。可以对 `RunState` 生成合法状态和动作，钉住：拒绝不改状态；生命在合法区间；卡牌不无故增减；同一奖励不能领两次；卸下的遗物不再生效；池中每条内容都有可达路径；同一种子加同一动作序列结果一致。

随机 Soak 不能代替定向场景。`web/soak_test.mjs` 不要求 `eliteFights >= 1`，注释写明了原因：新手策略的随机游走大约死在 6–8 层，而第一幕精英更深。这是诚实的，不是漏写。它还有条件断言：若精英打赢了，奖励必须出遗物；若到了篝火，必须点过打铁。条件断言证明不了「精英战在浏览器里一定可玩」。精英、Boss、特殊药水仍要固定夹具，不能靠运气遇见。

另外，WASM 第一阶段不必每次改 UI 都跑固件和历史 RL 闸门。提交前快检和完整回归分开。

### 2. 按机制推进，不按物品数量推进

§158.7 已经把剩下 13 瓶药拆成机制，而不是 13 条数据：

| 共用机制 | 一次能带上的内容 |
|---|---|
| 战斗内选牌 | Attack / Skill / Power / Colorless Potion |
| 牌区选择与移动 | Elixir、Gambler's Brew、Liquid Memories |
| 改卡牌实例 | Blessing of the Forge、Snecko Oil |
| 自动出牌与复制执行 | Distilled Chaos、Duplication Potion |
| 死亡与战斗结束拦截 | Fairy in a Bottle、Smoke Bomb |

不要为每瓶药写一套特殊流程。玩家选择应是可序列化状态，不是 UI 回调里的临时逻辑。

运行层已经有 `Pending`（休息、商店、奖励、事件选牌、开局祝福）。缺的是**战斗内**决策，`rd-core` 里还没有对应类型。不要推倒现有 `Pending`。战斗侧补一个边界明确的待决操作即可，例如选牌来源、最少/最多张数、选完后的操作。同一机制应能服务卡牌、药水和事件，并让合法动作可枚举、可存档、可回放。

验收标准：再加一张同类卡或一瓶同类药时，主要改内容定义，不复制一套状态机。

### 3. 冻结外部语义，不冻结内部布局

长期稳定的应是：玩家可见规则、Action / Observation 语义、需要精确回放的随机数消费、内容版本与迁移、少数有意保留的顺序约定。

不应为了旧测试长期冻结私有函数签名、对象布局和数组容量。`MAX_RUN_DECK = 60`、`MAX_POOL = 64` 对原来的嵌入式目标有意义；第一阶段加大容量或改成动态容器，不是破坏游戏语义。只有它开始限制内容或造成静默错误时才换，能用的固定数组不必为了「现代化」先拆掉。

### 4. 遗物要绑生命周期，不能绑「看起来相关的函数」

Eternal Feather 是例子，不是孤例。`rest_heal()` 同时承担了百分比休息、Regal Pillow 和按牌数治疗，后两者的触发点并不相同。后续遗物应登记到进入房间、战斗结束、回合开始这类事件上，而不是直接改一个邻近的计算公式。

§159 有一条同方向的教训：A5 写的是「Boss 后回复 75% 而不是 100%」，查下去发现 100% 的基础规则根本不存在。先补基础事件，再挂修饰。不要实现一个关于不存在事件的分数。

### 5. 拆职责，不推倒架构

`rd-run/src/state.rs` 现为 4,600 行（原评审写 4,117，其后又加了 Ascension）。`rd-wasm/src/run.rs` 约 4,700 行，`lib.rs` 约 3,200 行。长文件本身不是错；状态机、规则、内容效果和错误处理混在一起时，改一处容易碰到别处。

可以逐步分开，不必一次新增六个 crate：

| 职责 | 现在大致在哪 | 以后宜独立的原因 |
|---|---|---|
| 整局状态与不变量 | `RunState` | 所有权要留在一处 |
| 动作校验与原子提交 | `buy_*` / `resolve_event` 等 | 现在失败点不统一 |
| 进房、遭遇、战斗结果 | `begin_node` 与 wasm 集成 | 运行层不应知道内容细节 |
| 奖励、购买、掉落池 | `roll_reward` / `pick_*` | 截断和权重容易分叉 |
| 遗物触发 | 散落在 `rest_heal` 等 | 触发点已经错了 |
| ABI 与 Session | `rd-wasm` | 不应再长规则 |

WASM 侧仍用 `static mut` 保存 `SESSION` / `RUN`，并返回可变静态引用。单线程、导出不重入时，作者认为这是 sound 的。但 `run.rs` 已经记录过一次真实别名：持有 `run_slot().as_mut()` 时再 `set_error` 会形成两个活引用，在 `rust-units` 里表现为访问违例（退出码 `0xC0000005`），后来用 `fail()` 绕开。所以这不是纯未来风险。P2：不要为它停玩法；新导出不要再手写第二份全局槽访问。对外 ABI 可以不变。

### 6. 开发日志保留，但不要再当唯一入口

`port-plan.md` 的优点是能追到某个 bug 怎么来的、怎么修的、哪条测试抓住了它。缺点是历史结论和当前结论叠在一起。§11.3 的内容体积后来被 §12 推翻，§157 的 Eternal Feather 描述和清单不一致，都是这种混写的代价。

保留 `port-plan.md`，不要删。另写三份短文档，只记仍然有效的事实：

| 文件 | 记什么 |
|---|---|
| `docs/status.md` | 当前能力、最近验证、已知缺陷 |
| `docs/roadmap.md` | 下一阶段目标和验收标准 |
| `docs/architecture.md` | 模块边界、状态所有权、Action / Observation |

README、源码注释和最新一节日志已经会不同步。短文档的验收是：和最新一节冲突时，以短文档为准，并在日志里留一条更正，而不是改历史段落。

## 五、第一阶段还缺什么

§159 之后，缺口不是「能不能跑」，而是机制是否完整、稳定、可重复。

| 方向 | 判断 | 优先级 |
|---|---|---|
| 规则一致性 | 有基础，但商店原子性、Eternal Feather 数值和时序仍错 | P0 |
| 选择型 / 复合效果 | 13 瓶药卡在共用机制上 | P1 |
| 遗物生命周期 | 触发点还绑在计算函数上 | P1 |
| 卡牌与遭遇 | 可玩，和 Ironclad 清单仍有差距；30 含升级行 | P1 |
| 单局路径 | 三幕结构 ≠ 精英、事件、商店、休息都正确组合 | P1 |
| Ascension | 20 条里实现了 9 条；未实现的 11 条已列在 §159.6，不要标成支持到 A20 | P1，按机制做，不按等级号刷 |
| 存档 / 读档 | 浏览器入口还没有版本化快照闭环 | P2 |
| 回放 | 有种子和哈希，还没产品化成「动作序列 + 每步哈希」 | P2 |
| UI | 已有 E2E；种子和等级输入是 §159 新加的，缺参在 wasm 里会当成 0 | P2 |
| 原生端 / MCU 内存 | 第一阶段不需要 | 暂缓 |

不要把「移植完全部原版卡牌、药水、遗物」当成下一阶段唯一完成标准。那会回到逐项适配、逐项修错。

更合适的目标是一条机制完整的垂直切片：走完一幕，覆盖普通战、精英、Boss、事件、商店、休息点、药水和遗物，并且这些系统能组合。已有路径列为回归，不重复开发。

§159 还有一条要守住的纪律：做不到的规则写出来，不要静默不生效。A1 的精英频率、A10 的不可移除诅咒、A12 的「奖励里还没有强化牌」、A20 的双 Boss，都是这种形状。A7/A8/A9 的 +10% 生命是标明了的近似，不是 wiki 数字；以后 `ENCT` 有了 ascension 列，应删掉这个常量，而不是让两套数字并存。

## 六、建议的开发顺序

1. **正确性补强。** 修商店原子性、池截断、Eternal Feather 的公式、触发点和稀有度；顺手核对 Golden Idol 是否该进掉落池。每个已知缺陷一条回归，并且故意还原旧写法时测试失败。
2. **通用决策与遗物事件。** 战斗内选牌、目标选择、牌区操作、延迟执行；遗物挂到生命周期事件。复用现有 `Pending` 和效果执行，不另起一套。
3. **一幕垂直切片。** 精英、Boss、商店、事件、休息点各有一条确定性浏览器场景。随机 Soak 通过不够，指定路线要从开局走到幕末。
4. **存档与回放。** 版本化快照含整局状态、战斗状态、RNG、待决决策、内容版本，外加动作序列和每步哈希。刷新后能继续；同一回放能复现关键状态。
5. **按已有机制批量加内容，并打磨反馈。** 加内容不应再改基础执行器。

## 七、第一阶段应主动放下的

原计划围绕 MCU、RL 和多目标，所以大量使用固定容量、显式边界和少分配。这些选择当时没错。WASM 优先时，它们应退到次要位置。

暂时不追求 `no_std`、零堆分配、极小 WASM、ESP32-P4 适配，以及为潜在嵌入式需求做的复杂结构优化。也不必反向推翻能工作的固定数组。

仍要守的性能纪律只有一条：每次 Action 不要做明显的全局状态复制、不可控循环或无意义序列化。`Vec`、`String`、`HashMap` 和堆分配不是禁区。整数规则继续保持，不要为了方便引入浮点。

## 最终判断

规则执行与内容分离、确定性验证、持续回归，这三样已经是可用的引擎基础。

需要警惕的趋势是：测试数量涨得很快，部分规则错误仍能通过全部现有验收。下一阶段最值得投入的不是再加闸门，也不是换一套架构，而是让状态转换错误、事件时序错误和内容边界错误系统地失败。

若只能做一件架构工作：统一状态变更和生命周期事件的语义。若只能做一件流程工作：把测试从「覆盖典型案例」抬到「验证不变量和真实交互」。
