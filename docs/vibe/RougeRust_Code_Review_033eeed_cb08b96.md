## 0. 执行摘要

**总体判断：方向正确，机制设计与测试实践明显改善；但存在一个需要优先处理的 WASM 存档缓冲区问题，以及若干状态一致性和接口契约缺口。**

这轮 Agent 的亮点不只是修复旧问题，而是形成了更好的工程闭环：**规则契约 → 最小实现 → 定向测试 → 负向验证 → 浏览器验收**。尤其值得保留的是：定义与实例分离、逐实例出牌、定向浏览器切片和以负向变异验证测试有效性。

最需要进一步加强的能力是：**在跨模块、跨调用阶段、可能部分失败的复合操作中，系统性保证状态不变量和所有权契约。**

## 1. 具体问题（按优先级）

### P0 — 存档缓冲区与 WASM scratch 容量不匹配

**涉及位置**：`kernel/rd-wasm/src/lib.rs`、存档模块 `archive.rs`、浏览器存档／回档调用。

WASM 通用 scratch 缓冲区仅 1024 字节：

```rust
static mut SCRATCH: [u8; 1024] = [0; 1024];

pub extern "C" fn rd_env_scratch_buf() -> *mut u8 {
    std::ptr::addr_of_mut!(SCRATCH) as *mut u8
}
```

新存档模块则允许最多 16384 字节：

```rust
pub const MAX_ARCHIVE: usize = 16384;
```

导出路径 `rd_run_archive_into(ptr)` 未接收目标容量，无法证明目标可容纳整个存档。浏览器侧取得 `rd_env_scratch_buf()` 后直接使用该指针；回档时把用户粘贴的文本写入 scratch，也缺少针对该缓冲区实际容量的检查。

**影响**：

- 现有短存档恰好不超过 1024 字节，不代表未来合法存档仍然安全。
- 较长存档或外部输入可能写出 scratch 对象边界。
- 即使地址仍位于 WASM 线性内存内部，线性内存检查也不能保证对象级越界被拦截。
- 实际破坏的对象、故障表现仍需动态验证，不应断言固定后果。

**建议**：

1. 明确 `rd_run_archive_into(ptr, capacity)` 的容量契约；返回实际写入长度或明确错误码。
2. 为存档分配足够的独立缓冲区，或使用由 WASM 分配、经 API 暴露长度和生命周期的内存；不要沿用固定 1 KiB 通用 scratch。
3. 浏览器拷贝输入前，根据 **实际字节数** 与目标容量进行检查。中文及非 ASCII 字符不能用 JS `string.length` 代替 UTF-8 字节数。
4. 增加 1023、1024、1025、16384 字节及超限输入测试，并对导入、导出分别测试。

**完成标准**：长度超过可用容量时，接口稳定拒绝且不写出缓冲区；正常最大容量范围内的存档可无损传递。

### P1 — 存档 Round-trip 未覆盖删除卡牌后的状态

**涉及位置**：`kernel/rd-run/src/state.rs` 的 `remove_card()`、`archive.rs` 的 `write_payload()`、存档往返测试。

删除卡牌时，有效区间左移，`deck_len` 减一，但旧的最后一格未清空：

```rust
for index in card..(self.deck_len as usize - 1) {
    self.deck[index] = self.deck[index + 1];
}
self.deck_len -= 1;
```

存档只写入前 `deck_len` 项；恢复时数组从空状态重新构造。因此，删除卡牌后，恢复态与原态的**非活动尾部**可能不同，结构级 `assert_eq!(restored, run)` 不一定成立。

需要区分：这说明“结构完全相等”的强 Round-trip 契约存在盲区，**不等于已证明玩家游戏行为发生差异**。

**建议**：

- 短期：删除后规范化清空非活动尾槽，并为其他固定容量数组建立相同不变量。
- 长期：明确“物理结构相等”和“逻辑／未来行为等价”的区别，只把真正影响未来行为的部分作为序列化契约。
- 新增购买、删除、升级、奖励领取、商店访问等状态的 Round-trip 测试。

**完成标准**：所有可达的典型状态变化后，存档与恢复满足明确写在测试中的相等／等价契约。

### P1 — 存档合法性不能仅由浏览器 UI 判断

**涉及位置**：`rd-wasm/src/run.rs` 的 `archive_text()`，浏览器的 `mode` 判断，`rd_run_restore_from()`。

新存档不包含完整战斗状态，因此战斗进行中不应允许整局存档或回档。现有实现将关键校验移入浏览器 UI；底层接口未一致地强制这一契约。

重构的初衷是解决“已结束但未清理的战斗 Session 误阻止存档”。**正确修复对象应当是 Session 生命周期表达，而不是把权威业务校验下放给 UI。**

**建议**：

1. 在拥有权威游戏状态的层明确表示 `Idle / Fighting / Finished`，或至少引入语义清晰的 `fight_active`。
2. 在战斗开始／结束的确定时刻更新它。
3. 存档与回档的 WASM ABI 统一检查该状态，浏览器的禁用按钮仅为交互反馈。
4. 回档提交时同步失效化或重建临时战斗 Session，避免跨模块状态不一致。
5. 直接调用 ABI（绕过网页）进行非法时序测试。

**完成标准**：即使绕过 UI，战斗中仍无法完成不合法的存档／回档；回档成功后，Run 与战斗 Session 生命周期一致。

### P1 — 通用选牌机制可能发生部分提交

**涉及位置**：`rd-core/src/state.rs` 的 `resolve_choice()` / `resolve_from_pile()` 与卡牌 mark-counter 逻辑。

当前实现会先验证部分前置条件，再执行一系列带 `?` 的状态修改。例如：

```rust
for &slot in &slots[..picked] {
    self.move_card(...)?;
    if choice.then == ChoiceThen::ToHand && cost_delta != 0 {
        self.write_price(slot, cost_delta)?;
    }
}
self.choice = None;
if choice.then == ChoiceThen::DiscardThenDraw {
    self.draw_cards_with_reshuffle(...)?;
}
```

如果 `write_price()` 因 mark-counter 槽位已满而失败，或后续其他可失败步骤报错，则之前的卡牌移动可能已经生效。存在“预校验覆盖范围不等于全部失败来源”的风险。

**建议**：

- 构造 mark-counter 已满的测试牌，并提交带费用改写的选牌请求。
- 失败时对比完整状态，包括牌区、费用、Pending Choice 和必要时的 RNG 状态。
- 对所有提交后仍可能失败的步骤，要么在提交前完整校验与预留容量，要么采用临时状态提交／其他可证明原子性的方式。

**完成标准**：拒绝操作在约定的全部可观察状态上无副作用；至少有能主动触发原错误路径的测试。

### P1/P2 — `DiscardThenDraw` 的容量判定过于保守

**涉及位置**：`rd-core/src/state.rs` 的选牌结算。

若操作先丢掉 `picked` 张手牌，再抽牌，目标牌区的容量应按动作的实际先后顺序计算。现有 `hand_count + picked > MAX_CARDS_PER_ZONE` 形式的判断可能错误拒绝“虽然手牌接近上限，但先丢牌腾出了空间”的合法操作。

**建议**：明确 `DiscardThenDraw` 的语义，按实际状态转换顺序计算有效容量；为接近容量上限的合法与非法路径分别补测试。

### P1 — 回档缺少完整的状态语义验证

**涉及位置**：`archive.rs` 的 `read_payload()`、`rd_run_restore_from()`。

目前解析过程覆盖一些格式、长度和枚举检查，并使用临时对象完成提交；但还需要在提交前对游戏逻辑进行系统性校验：

- `health`、`health_max` 与其他基础数值的约束；
- 幕数、楼层、当前节点和地图关系；
- `pending` 与当前房间／阶段是否匹配；
- 商店与奖励状态是否自洽；
- 卡牌、遗物、药水 ID 是否存在于当前内容版本；
- 必要的版本兼容性约束。

推荐流程：

```text
解析存档
  ↓
验证格式与版本
  ↓
构造临时 RunState
  ↓
RunState::validate_invariants()
  ↓
验证内容引用与内容版本
  ↓
原子提交
```

CRC32 可识别部分偶发数据损坏，但**不是**状态合法性证明，也不是用于抵抗人为篡改的安全机制。

另建议补充 `Reader::int()` 将 `u64` 转成 `u32` 前的范围检查，以及 `Reader::var()` 对畸形／非规范 varint 的拒绝测试。

### P2 — 浏览器切片测试并不等同于真实指针点击

**涉及位置**：`web/act1_slice.mjs`。

现有测试用 `dispatchEvent(new MouseEvent("click", ...))`，部分还直接调用 `element.onclick()`。它可以覆盖 DOM 事件处理器和相应业务逻辑，但不能可靠验证元素被遮挡、无法点击、命中区域错误、`pointer-events` 异常等真实交互问题。

**建议**：保留这些快速测试；另选少量关键路径，用 CDP `Input.dispatchMouseEvent` 或 Playwright 的真实指针操作验证可点击性。没有必要全面重写已有脚本。

## 2. 值得保留和沉淀的优秀实践

| 实践 | 价值 | 建议沉淀方式 |
| --- | --- | --- |
| 商店购买先校验／完成可能失败的写入，再扣费 | 以最小改动实现失败原子性 | 在 Action 设计评审中固定检查“提交点” |
| 故意恢复错误逻辑，验证测试会失败 | 避免“测试通过但无法发现原 Bug” | 回归报告附一条负向变异结果 |
| 选牌候选保留定义 ID，确认后才生成实例 | 保护实例 ID、序号与状态哈希语义 | 写入内容定义／实体创建规范 |
| 新增 `HeroPlaysInstance` 而不偷改 `HeroPlays` | 兼容冻结语义并表达精确的实例级操作 | 冻结 ABI 与语义扩展规范 |
| 确定性一幕场景覆盖商店、事件、休息、精英和 Boss | 不依赖随机 Soak 恰好触发关键路径 | 关键玩法路径的固定测试夹具 |
| 谨慎评估 Clippy 警告而非直接禁用 | 防止“为全绿而掩盖语义问题” | 警告处理记录和待办追踪 |

### 两项特别值得制度化的实践

**定义与实例分离**：候选选项在被确认前应当是定义层的描述，不应提前占用游戏世界中的实体 ID 或产生无意义状态更改。只有操作确认时才创建真实实例。

**精确语义扩展，而不是暗改旧契约**：当旧的 `HeroPlays` 根据卡牌定义寻找实例、而 UI 需要操作具体手牌时，用 `HeroPlaysInstance` 表达新需求是合理做法。已冻结语义若需变更，应显式标明兼容性影响。

## 3. 对上一轮建议的理解偏差

### 3.1 原子性：原则理解正确，复合操作的证明仍不充分

商店购买修复值得肯定；但通用选牌依然有“预先检查了部分条件，实际提交过程中还可能失败”的风险。

应采用统一判断标准：

> **任一返回 `Err` 的操作，都必须证明在该错误路径上不会留下违反契约的部分提交。**

不要求每次都完整复制大状态，但必须证明失败路径安全。

### 3.2 状态所有权：把权威校验移到了错误的层

“不要过分耦合 UI”不是让 UI 独自决定动作合法性。权威游戏状态所在层必须自己守卫操作；UI 的禁用、隐藏和提醒只是额外体验。

对于已结束但尚未清理的战斗 Session，应修正 Session 生命周期表示，而非只在网页判断 `mode`。

### 3.3 `no_std` 与固定容量：没有必要反向全盘推翻

Agent 反对为使用动态容器而无收益地重写已经正常工作的固定数组，这一点是合理的。

但第一阶段的优先级已经明确调整为 **WASM 玩法正确性与开发效率**。因此：

- 已实现且没有开发负担的 `no_std` 或固定容量设计可以保留；
- 当资源约束显著增加功能复杂度、产生静默截断或接口风险时，应允许为 WASM 选择更简单的动态方案；
- 暂时不必围绕 MCU 最终内存预算继续增加新的复杂性。

手写存档协议由 varint、RLE、base64、CRC、固定缓冲区等组成，维护表面积较大。对于第一阶段，应评估更简单的版本化序列化方案（如 `serde`），但**不要求立即推翻已经工作的实现**。

### 3.4 目标玩法语义与参考实现语义要区分

逐实例折扣等规则可能与原版《Slay the Spire》的某些持续时机不同。若属于刻意偏离，应在测试契约中清楚标注；若目标是参考代码精确兼容，则需要修正。

## 4. 建议纳入 `AGENTS.md` 的通用开发契约

以下内容可在评审确认后提炼进入项目的 `AGENTS.md`，**不要视为本报告已修改仓库或已获得新增功能授权**。

### 4.1 授权边界

只修改本任务明确要求的模块与行为；不得顺手添加功能、重写架构、扩大兼容性范围。若发现确需扩展范围的高风险问题，先呈报证据和拟议方案。

### 4.2 权威状态与职责归属

游戏规则由持有权威状态的层校验；UI 只负责显示和交互反馈，不得成为非法动作的唯一防线。

### 4.3 每个 Action 的状态不变量

在实施前说明：前置条件、可失败步骤、提交点、失败后的状态保证、随机数消耗语义。不能仅凭有预校验就宣称原子性。

### 4.4 跨模块接口契约

对所有缓冲区、序列化接口和 FFI/WASM 导出，明确：可写容量、有效长度、输入编码、对象生命周期、错误语义及版本兼容性。严禁默认调用方提供“足够大”的内存。

### 4.5 测试必须能证伪

除成功路径外，覆盖拒绝路径、边界值、回放一致性及真实浏览器入口。针对修复过的 Bug，至少有一条负向验证证明对应测试可以在旧错误重新出现时失败。

### 4.6 维护冻结语义

优先保持对外可观察规则、Action/Observation、必要的 RNG 消耗语义和版本契约稳定。内部实现可为提升正确性与可维护性而重构，但需要界定回归范围。

### 4.7 诚实报告验证状态

验收报告必须区分：**实际执行通过**、**静态检查**、**未验证**与**已知风险**。不得把仓库历史测试结果说成本轮已复验；不得以总测试数量替代关键行为覆盖。

### 4.8 第一阶段优先级

WASM 游戏功能、规则一致性和开发效率优先；不因尚未要求的 MCU 内存预算而增加复杂性；保留已经稳定且无负担的约束。
