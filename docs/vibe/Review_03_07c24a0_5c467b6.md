# RougeRust 第三轮增量代码审查

- **范围**：`07c24a0^..5c467b6`（截至 `5c467b6`，开发记录 §161.10–§169）
- **目标**：WASM 优先、玩法与状态正确性优先；不以 MCU 内存预算或临时 UI 的视觉完善度作为阻塞条件。
- **方法与证据等级**：阅读公开仓库中的开发记录与关键源文件，做静态审查；**未在本地独立编译、运行、进行 Miri/故障注入复验**。仓库记载的 806 个单元测试、20/20 验收闸门只代表项目自身记录。
- **判定口径**：P0=潜在 UB / 必须优先解决的安全性问题，P1=明显的规则或契约漏洞，P2=后续可维护性建议。P0/P1 不代表已经独立动态复现。

## 1. 总体判断

这轮重构有效回应了上一份 Review：存档缓冲区拥有独立容量契约；`remove_card` 清理非活动尾槽；选牌在移动前检查费用计数器容量；`DiscardThenDraw` 不再错误要求额外手牌容量；扩充既有 `RunState::check_invariants`；增加动作回放、内容指纹和内容表格式版本；增加真实指针点击与像素性质测试；更新长期漂移的项目文档。

**建议保留这些方案，不做大范围推倒重建。** 本轮新增风险主要在 `rd-wasm` 中的回放和战斗生命周期边界，而不在 `rd-run` 的核心不变量框架。

## 2. Findings（按优先级）

### P0-1：回放期间可能产生重叠的全局 `&mut` Session 引用

- **源码**：[rd-wasm/src/run.rs L3186–3298](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3186-L3298)，[run_slot 的实现 L237–249](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L237-L249)，[rd_run_step L837–859](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L837-L859)。
- `rd_run_replay_from` 先把 `run_slot().as_mut()` 的引用绑定为 `session`，再在循环中调用 `rd_run_step`、`rd_run_begin_node` 等；后者再次取得同一全局状态的可变引用。
- 原 `session` 在循环内的错误分支继续使用，存在重叠可变别名及 UB 风险；“同线程、没有并发”并不消除这个问题。
- **最小修复**：只短暂借用 Session 设置 `replaying`；随后释放引用再调用导出函数；比较哈希、更新诊断数据时各用短作用域。更长期可抽出接受 `&mut RunSession` 的内部 `apply_record`，ABI 和回放共用同一执行逻辑。
- **测试**：加入含多步、带解析失败分支的回放测试；配合专门的别名风险审查及适当动态工具。不能把已有测试通过视为 UB 已排除。

### P1-1：`fight_begin` 先设置 `in_fight`，后执行可失败初始化

- **源码**：[run.rs L2763–2857](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L2763-L2857)。
- 函数提前写 `elite_fight`、`boss_fight`、`in_fight = true`，随后仍可能因遭遇池缺失、选择失败、战斗构造失败、遗物效果应用失败而返回 `-2`，没有回滚。
- **影响**：初始化失败后游戏可能没有正常可用的战斗，但存档/回档判断仍认为在战斗中；有些失败路径还已消耗 RNG、安装半初始化的战斗 Session。
- **建议**：把构造与验证放在提交前，`in_fight=true` 仅在整个初始化成功后设置；必要时使用临时快照/事务性提交，或明确不可回滚错误为 fatal 并恢复会话。
- **测试**：缺遭遇池、坏战斗内容、遗物初始化错误三类故障注入，均断言会话标记、RunState、RNG、战斗 Session 保持约定的不变量。

### P1-2：`fight_begin` 没有拒绝重复开始战斗

- **源码**：[run.rs L2712–2765](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L2712-L2765)。
- 目前有“必须处于战斗节点”“节点未结算”等检查，但没有 `if session.in_fight { ... }`；战斗未结束时节点一般仍未结算，直接重复调用可以继续走到重新选遭遇和构造 Session。
- **建议**：入口先拒绝 `in_fight=true`；对拒绝前后 RunState、RNG、已有战斗指纹做不变性测试。

### P1-3：脚本导出/回放只由浏览器模式限制，ABI 没有同等防线

- **源码**：[rd_run_script_fill L3053–3073](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3053-L3073)，[rd_run_replay_from L3125–3185](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3125-L3185)，[页面 L2064–2110](https://github.com/tk166/RogueRust/blob/5c467b6/web/index.html#L2064-L2110)。
- 页面 `mode === "fight"` 会阻止脚本操作，但导出接口本身没有校验 `in_fight`；`rd_run_replay_from` 甚至会重新 `rd_run_start`，摧毁现有运行状态。
- 上次修复存档时已明确了状态所有权规则，这里应沿用。给 `script_fill`、`script_into` 和 `replay_from` 加上相同的 ABI 级检查，并用绕 UI 的测试验证拒绝。

### P1-4：`run_hash` 容量失败被降级为合法的零值

- **源码**：[rd-run/src/hash.rs L193–205](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-run/src/hash.rs#L193-L205)，[rd-wasm/src/run.rs L196–235](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L196-L235)，[L3295–3305](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3295-L3305)。
- `run_hash` 遇到 8 KiB 文本上限会返回 `None`，但调用方 `hash_prefix(...).unwrap_or(0)` 将失败映射为正常可比较的整数 0。
- **风险**：如果两个不同状态都溢出，其哈希都会成为 0，从而产生假阳性。能否在正常内容达到该上限尚未独立验证。
- **建议**：将失败传播为明确错误，绝不使用 0 代替哈希；针对满牌组、最长合法 ID、最繁忙商店等构造上限测试。

### P1-5：新暴露的 `rd_run_script_into(ptr)` 没有容量参数

- **源码**：[run.rs L3085–3099](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3085-L3099)。
- 与已修复的存档缓冲区问题类似，此 ABI 可以按脚本长度向任意指针写入，但函数本身不知道目标容量。其 `unsafe` 文档规定调用方必须预留空间，因此在正确使用的 Rust 调用者下有契约；对 WASM/JS 的裸指针 API 仍然容易被误用。
- 当前页面使用带界限的 `script_fill`，**不是页面已被证实越界**。建议对外删除/不暴露 `_into` 或扩展为 `(ptr, capacity)`；拒绝超过容量的写入。

### P2-1：回放是破坏性操作，建议区分“验算”与“加载”

- **源码**：[run.rs L3166–3180](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L3166-L3180)，[页面 L2108–2130](https://github.com/tk166/RogueRust/blob/5c467b6/web/index.html#L2108-L2130)。
- 当前回放会覆盖正在进行的整局，并在分叉点留下部分回放状态；页面代码明确承认并重画 UI，属于**有意设计**而非隐藏 bug。
- 但是回放主要用来调试、验收时，最好提供不修改玩家当前局面的 `verify_replay`：使用临时 Session 或独立 WASM 实例，返回步骤差异；另设明确的“载入回放”按钮。第一阶段可以先用 UI 警告而非立即重构。

### P2-2：日志的证明能力需要明确边界

- 回放保存的是 **Run 层动作及战斗结果**，不是完整 Combat 的出牌序列，因此“整局回放一致”不等于“战斗行为被逐动作重演”；这是当前实现明确的范围选择，合理但需文档说明。
- 当前回放执行各导出动作时多处写 `let _ = ...`，主要依赖状态哈希。对于拒绝动作（状态不变），行为返回码发生变化未必能被哈希发现。若想验证 API 语义本身，日志可额外记录结果码/动作是否成功。

### P2-3：战斗 DeckEntry 使用 `Box::leak`

- **源码**：[run.rs L2803–2820](https://github.com/tk166/RogueRust/blob/5c467b6/kernel/rd-wasm/src/run.rs#L2803-L2820)。
- 每次开战通过 `Box::leak` 永久泄漏一次牌组记录。这可能是沿袭旧实现，并非可归责于本轮提交的新问题，且单场体积不大；但在浏览器长期会话里会累积，建议未来将其所有权并入 Combat Session。**当前不以微小内存优化为优先，但内存泄漏与内存预算是两个不同问题。**

## 4. 值得沉淀的最佳实践

1. **唯一权威验证入口**：从既有 `RunState::check_invariants` 扩展而不是复制一套 `validate`。
2. **错误路径的对抗性验收**：故意退回旧错误，验证测试在预期断言处失败。
3. **结构化快照 + 增量动作日志 + 逐步哈希**：能定位首次分叉；需要把“不能计算哈希”与“哈希不一致”区分。
4. **内容“身份”与“可读性”分离**：整个镜像的指纹用于存档归属，schema/stride/version 用于解析器能否理解，二者不能互代。
5. **表目录只定义一次**：`Table::ALL`、`Table::stride()`、内容检查与构建验证由一致性测试约束，新增表不能悄然漏检。
6. **衍生数字由工具计算**：README 和缺口清单不用手抄会随代码漂移的数量，必要时把脚本输出作为单一真实来源。
7. **视觉测试优先性质而非全图基线**：对必要的交互可见性、遮挡、溢出写少量稳定断言；使用故障注入证明探测器有效。
8. **第一阶段 WASM 优先**：保留既有 `no_std` 等合理约束，但不为未来 MCU 预算引入新的功能开发障碍。

## 5. 对 Agent 的设计理解评价

基本正确：原子性、唯一来源、不变量、版本化、真实浏览器交互的目标都已有效吸收。没有必要因为仍有新问题而否定整体架构。

尚未完全内化的规则：

- **生命周期状态必须成功后提交**，不能只因为一个字段被引入就认为状态机已经可靠（`fight_begin`）。
- **同类新 ABI 必须继承旧 ABI 的合法性约束**，不能在 `archive` 做到、在 `replay` 再次交给 UI。
- **`static mut` 全局状态必须避免活跃借用跨回调/导出调用**，单线程不能替代 Rust 别名规则。
- **错误不能用某个合法数据值掩盖**：`None` 哈希不得退化为 0。

## 6. 推荐下一轮最小改动计划

1. **P0**：消除 `rd_run_replay_from` 跨导出调用的可变别名；补专门回放回归测试。
2. **P1**：给 `rd_run_fight_begin` 增加“战斗已开始”的拒绝；保证初始化失败不会留下 `in_fight`/RNG/Session 半状态。
3. **P1**：为脚本导出和回放加 ABI 层的 `in_fight` 守卫；绕 UI 直接测试。
4. **P1**：传播哈希容量错误；对新 `script_into` 加容量参数或取消暴露。
5. **P2**：明确回放是否可覆盖当前局面；若定位为调试工具，提供非破坏性校验方式。
6. **P2**：保留像素测试 Demo，不扩张到临时 UI 的每个页面，也不因其阻塞玩法开发。

建议每项修复的验收报告均包含：原缺陷的最小复现、修复前为什么会失败、修复后实际执行的测试、可反证的负控、未验证项。**不要把 20/20 闸门覆盖不到的条件写成“已经证明正确”。**

## 7. 结论与限制

本轮重构显著提高了工程质量，最有价值的进步是单一状态验证入口、拒绝路径上的不变量检查、内容版本化、确定性回放和自动化验收的反证意识。应当保留现有分层、避免扩大重构范围。

最重要的新发现是：**底层规则的验证已经较强，但新的 WASM Session/ABI 生命周期仍可绕过或破坏这些契约**。下一轮应针对这条边界做最小修正，而不是重写架构、增加视觉门禁或继续堆叠内容。

**审查限制**：以上结论是公开仓库指定快照的静态分析，未独立运行项目、没有提供动态复现证明；P0/P1 风险需由本地 Agent 实测确认，尤其是借用别名风险与故障初始化可达性。
