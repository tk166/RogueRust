# P1 —— R3F 技术 PoC 的实测结论

> 产物：`web-next/`（Vite + TS + React 19 + R3F 9 + three 0.187 + `@react-three/uikit` 1.0.78）
> 闸门：`tools/acceptance.ps1` 的 **[25/25] `ui-next`**
> 证据：本文 + `docs/ui-next-p1/*.png`（390×844 三态 + 1280×800）+ `font-measure.json`
> 基线：commit `9313c73` 之后；**这一阶段一行 Rust 都没改**

---

## 0. 一句话结论

**3D 这条路可以走。** 但"中文可读"不是靠"把牌做大"解决的 —— 390×844 上 10 张牌
**物理上放不下 10 个中文标题**（实测每张只露出 33px）。所以 P1 的答案是
**三维牌身 + DOM 文字覆盖层 + 三档可读性**（手牌 / 选中 / 详情），而不是"三维中文文字"。

字形图集的代价也量出来了：当前玩家词汇 **156 个字形**，子集化后微软雅黑 **64 KB woff2**、
黑体 **20 KB woff2**；DOM 覆盖层的增量是 **0 字节**。这就是选 DOM 文字的理由。

## 2. 中文可读性：这一节是 P1 的真正产出

### 2.1 实测：390×844 上放不下 10 个标题

| 量 | 数值 | 怎么来的 |
|---|---|---|
| 每张牌的**矩形**宽度 | 约 105 px | 0.62 世界单位 × 170 px/单位 |
| 相邻牌**中心间距**（stride） | 约 33 px | `2 × spread / 9` |
| 每张牌**露出来的宽度** | 约 33 px | `min(w, stride)` |

33 px 放不下任何 4 字中文标题（11 px × 4 = 44 px）。所以设计成三档：

| 档 | 触发 | 标题 | 规则文本 | 截图 |
|---|---|---|---|---|
| **手牌** | 常驻 | 露出的宽度 ≥ 44px 才显示，否则**只显示费用数字** | 不显示 | `390x844-hand.png` |
| **选中** | 按下并拖动（牌抬起、放大 1.32 倍） | 15 px | 12 px，不裁切 | `390x844-selected.png` |
| **详情** | 点开 | 20 px | 14 px，不裁切 | `390x844-detail.png` |

闸门守的是**不变量**，不是"某张牌恰好能读"：

> 每张牌 **要么**标题可读（≥ 11px 且 `scrollWidth ≤ clientWidth`），**要么**明确收起为紧凑态；
> 且每张牌的费用数字永远 ≥ 11px 且不裁切。

这条不变量比"标题字号 ≥ 11px"强：后者在紧凑态下无从判断（元素被 `display:none` 了，
`fontSize` 还是 11px —— 一个**看不见却合格**的假证据）。

### 2.2 字形图集体积（`native/ui_font_measure.py`）

只统计**面向玩家的字符串**（`sts/content/*.json` 的 name/desc + UI 标签），
**不扫源码注释** —— 第一版把 `Stage.tsx` 里 340 个中文注释字也算进去了，把"883 个字形"
这个数字整个抬虚。

| 字体 | 子集 TTF | 子集 WOFF2 | 完整字体 | 压缩比 |
|---|---|---|---|---|
| 微软雅黑 | 108 652 B | **64 408 B** | 19 704 352 B | 306× |
| 黑体 | 40 268 B | **20 116 B** | 9 745 792 B | 485× |
| **DOM 覆盖层（系统字体）** | — | **0 B** | — | — |

⚠️ **这是下限，不是最终数字**：156 个字形来自 12 张卡 + 8 状态 + 5 敌 + 5 遗物的中文字面量。
完整内容（30 卡 / 24 状态 / 9 事件 / 13 遗物 / 25 药水）还没有中文，按每字形约 400 B 外推，
真实图集大约在 **200–300 KB woff2**。这笔账在 P4 之前必须重算一次。

**另一条证据**：uikit 自带的默认字体 Inter 有 **423 247 B**，且**一个中文字形都没有**
（HUD 里的中文会渲染成豆腐块）。所以 P1 的 HUD 只用数字与拉丁字母，中文一律走 DOM。
这不是绕过问题 —— 这就是"3D 中文文字要付字体代价"的直接观测。

## 3. 体积与帧率

| 产物 | 原始 | gzip |
|---|---|---|
| `assets/index-*.js`（R3F + three + 应用） | 1 386 391 B | 393 897 B |
| `assets/inter-*.js`（uikit 默认字体） | 423 247 B | 284 319 B |
| `assets/worker-*.js`（yoga wasm） | 41 907 B | 12 215 B |
| `assets/index-*.css` | 2 692 B | 1 039 B |
| `index.html` | 633 B | 453 B |
| **合计** | **1 854 870 B** | **691 923 B** |

**Inter 那 284 KB gzip 是"只为了 HUD 里的 HP/EN/TURN"付的。** P2 应当换成一个拉丁子集
（或直接让 HUD 用 DOM），这是最容易砍掉的一块。

FPS（`window.__p1.fps()`，headless Chrome 软件光栅）：
`fps390 = 60–61`、`fps1280 = 60–61`。**这个数字不能当性能结论** —— 无头软件光栅既不代表
手机 GPU，也不代表桌面显卡。P1 只记录它，判据留给真机。

## 4. 闸门 25 抓到的东西（这部分比结论更有用）

P1 的代码里有五处**看起来对、实际错**，全部是闸门用真浏览器抓出来的：

| # | 症状 | 根因 | 形状 |
|---|---|---|---|
| 1 | "按第 3 张牌却打出了第 2 张" | 视觉网格自己接收 `onPointerDown`，而**回弹动画途中**的牌挡住了射线 | 命中目标在动 ⇒ 命中不可预测 |
| 2 | 被拖起的牌挡住敌人，目标永远命不中 | 同上 | 同上 |
| 3 | 390px 宽下 4 张牌跑到视口外 | `handSpread` 是 `useMemo([layout.width])`，而 `layout.width` 是**原地变异**的 ⇒ memo 永不重算 | 派生值缓存了"上一次的输入" |
| 4 | 中间那张牌**看不见也点不到** | 扇形 z 写成 `0.9 + |t| * 0.12`（对称），中间牌 z 最小，被左右邻牌完全盖住 | 视觉顺序与叠放顺序不一致 |
| 5 | 牌只剩一条边线 / 下半截消失 | 牌身颜色暗过背景；且**地台水平面一直延伸到相机前**，挡住了牌的下半截 | 深色主题里靠"边框"立不起来；UI 被世界几何遮挡 |

**修法（都已落地）**

1/2 ⇒ **视觉是装饰，命中要有静止目标**：每个槽位一块不可见命中面，位置**不跟动画走**；
视觉网格 `raycast={() => null}`。
3 ⇒ 扇形宽度**每帧从 `size` 算**（`fanSpread()`），不进 React。
4 ⇒ 叠放顺序**单调**（右压左），布局同时暴露 `hitX`（露出那条的中点）—— 闸门按 `hitX` 点，
不自己猜。
5 ⇒ 牌身提亮 + `depthTest=false` + `renderOrder`（手牌是 UI，永远画在世界之上）。

**还有三处是闸门自己的假绿**（比代码 bug 更值得记）：

- 只看"提交数变没变" ⇒ **没抓住牌**与**抓住了但被拒绝**分不开。现在每条负控先断言
  `phase === 'pressed' && handSlot === 期望值`。
- 只查"卡牌中心在视口内" ⇒ 牌身被裁掉一半也报通过。现在查**露出的宽度**与不变量。
- "选中态"先释放再截图 ⇒ 牌早回位了，测的是 `phase: idle`。现在 `mouseHold` 按住不放。

### 4b. `dist/` 入库的代价，以及堵法

闸门 25 要"不需要 npm、不需要网络"，所以 `web-next/dist/` **入库**。代价很具体：
改了 `src/` 却忘了 `npm run build`，闸门会去测**旧包**并报绿 —— 和 §350b 里
`--check-fixtures` 只看内容指纹是同一个形状（**度量报的是陈旧数字**）。

堵法：构建时把 `src/` 的 sha256 烘进 bundle（`vite.config.ts` 的 `__SRC_HASH__`），
闸门用**同一份** `web-next/scripts/src-hash.mjs` 现算一遍再比对。
负控：改 `src/` 不重建 ⇒ `FAIL ... built=cb28cb1ec9f9 live=8bee69e944df -- 需要 cd web-next && npm run build`。

另一半是**证据截图本身要可复现**：英雄呼吸与卡牌回弹都用 `clock.getElapsedTime()`，同一段代码
跑两次像素不同 ⇒ 每次跑闸门都让工作区变脏（三个 PNG 永远是 `M`）。所以闸门用 `?debug&still`：
呼吸时间固定 0、卡牌直接吸附。连跑两次截图的 md5 相同，工作区保持干净。
`still` 只冻结**视觉插值**，不冻结状态机 —— 拖拽/高亮/模态隔离照样走真事件。

## 4c. 合并第十三轮参考包之后（§353）

版面从"英雄居中、敌人左右"改成**左右阵营**（我方永远在左）：竖屏敌人在右侧单列（≤6，按密度
缩放），横屏两行 `ceil/floor`（每行 ≤3）。队形是纯函数（`stage/formation.ts`），业务 `slot`
原样带出，`>6` 或重复 slot 直接 `RangeError` —— 不静默截掉一个可攻击目标。

交互补齐（都是参考包带进来的）：唯一 `activePointer`（第二根手指不能偷牌）、**真实位移**
（8px 阈值终于有牙，之前四处都送 `999`）、`pointercancel`/`blur`/Esc 统一取消、长按 450ms
看详情、右键看详情、详情有可见关闭按钮、瞄准连线与面向相机的轮廓环（青=可选/绿=目标/红=非法）。

**合并后量出来的三处版面问题**（`native/_dbg_layout.mjs`，不是看截图猜的）：

| 现象 | 数字 | 修法 |
|---|---|---|
| 手牌压底部操作栏 | 390×844 卡底 804 / 操作栏 790 起；1280×800 卡底 817 > 800 | 扇形 `y` 0.72 → **0.66** |
| 竖屏敌人标签互压 | 两敌只隔约 114px，三行标签约 60px | 竖屏间距上限 1.0 → **1.35** |
| 提示气泡盖住 HUD | 气泡 top=14、HUD 14–100 | 窄屏 `top` → 100px |

⚠️ 第一条的教训：我原来按 z=0 平面算"装得下"，但手牌在 z≈0.9（离相机更近）⇒ **透视下更大更低**。
**投影不是线性的，别拿另一个平面的比例去推** —— 这也正是闸门 25 新增的四条版面断言的理由
（只查"牌心在视口内"会让牌身被裁掉一半也报绿）。

## 4d. 两条「同一个事实两个来源」（§354）

**文字锚点**：紧凑态的文字落在**露出来那条**的中心（`hitX`），不是牌心。叠放是右压左，牌心
可能被右邻盖住 —— 文字放牌心等于把费用数字塞到邻居底下。负控退回牌心 ⇒ 偏差 **18px**（阈值 2px）。

**hover 单源**：原来"哪个敌人被指向"有两处（R3F 射线 vs 屏幕命中，半径 `r+14`），边缘会
"绿环亮着但没有 hover 高亮"。现在 `window.pointermove` 常驻，一次算出「指针下是谁」（视觉）
与「是不是合法目标」（提交），两者由**同一个** `enemyAtScreen` 回答。R3F 只负责卡片上的按下。
闸门把指针放在**敌人轮廓外、触摸半径内**（`r+10`）来钉这条 —— 中间点测不出来（旧实现在
中心也一致）。

顺带修掉：hover 抬牌原来把 z 推到 1.32，而手牌 `depthTest=false` + 固定 `renderOrder` ⇒
**z 根本不影响叠放**，透视下只会让牌更大更低（底边掉出视口 817 > 800）。改成 per-card
`renderOrder`（静止 `10+i` / hover 25 / 抬起 30），hover 只抬 y。

## 4e. 版面收进一个纯函数（§355）

`stage/combatLayout.ts` 现在是版面的**唯一来源**：相机距离、可见范围、手牌扇形
（`fanSpread` / `fanCenterY` / `fanArc`）、以及四块区域 `regions`（HUD / 战场 / 手牌 / 操作栏，
CSS 像素）。手牌的中心高度由"**底边贴着操作栏**"反推 —— 之前那个 `-halfH * 0.66` 是量出来的
魔法数，现在它有推导了。

三个直接后果：

1. **提示条位置由模型驱动**（`--hint-top` = `regions.hudBottom + 6`），CSS 不再有第二份 HUD 高度；
   闸门也拿同一个值断言（原来写死 `hintTop >= 96`）。
2. **闸门能断言"东西没跑到别人的区域里"**：敌人整个落在 `combatTop..combatBottom`、
   手牌底边不越过 `actionsTop`、气泡在 `hudBottom` 之下。这些断言都用同一个函数算出来的值。
3. **手牌数量 1–12 张都是纯函数的一部分**：`?debug&hand=N` + 闸门跑 1/3/12 三档
   （12 张时 stride ≈ 29px、全部紧凑态、最右那张仍点得到）。

另两项审阅遗留一起做掉：**四角投影**（原来只投中心 + 一个未旋转的角，牌斜 15° 时宽高会偏；
现在取四角外接矩形，另给文字一个 `faceW` = 牌面宽度）与 **`CardEdge` 几何体共享**
（原来十张牌十份 `EdgesGeometry`）。

⚠️ 一个已知的版面取舍：操作栏按**整条带子**预留（56px 全宽），所以左下角有空白。要与 StS
一样让手牌贴底，得把底部按左右分区而不是整条带子 —— 留给 P2。

## 5. 一条产品决策（与旧页面的**有意**分歧）

旧 `web/ui_render.js::actionFor()` 在"该牌只有一条合法动作"时，拖到**任何位置**都算数：

```js
if (list.length === 1) return list[0].actionIndex;   // 旧行为
```

这把"不需要目标的牌"与"需要目标、但只剩一个敌人"在拖拽层合并了。3D/触摸下这是**误触直接出牌**。

**P1 的选择**：**有目标的牌必须落在合法目标上**；落在空白处一律回弹，**不管场上剩几个敌人**。

| 情形 | 旧页面 | P1 |
|---|---|---|
| 无目标牌，拖到空白 | 出牌 | 出牌（不变） |
| 定向牌，多敌，拖到空白 | 拒绝 | 拒绝（不变） |
| **定向牌，单敌，拖到空白** | **直接打它** | **回弹**（分歧） |

理由：① 3D 里敌人是可拖上去的实体，"丢在空白处"读作"放回去"；② 规则不依赖"场上还有几个
敌人"这种隐藏状态。闸门里有一条专门守这个分歧（`只剩一个敌人时，定向牌丢在空白处仍然回弹`）。

> 这条是**输入层**的语义，不是内核规则。改它不动 Rust；parity 测试只锁业务语义
> （槽位不重排、拒绝时不替玩家选目标），不锁这一条。

## 6. 结构

```
web-next/
  src/input/pointerMachine.ts   纯函数状态机（pressed/dragging/targeting/commit/rebound）
                                + decide()：抬起时提交还是回弹，可穷举单测
                                + resultSeq：事件身份（同一动作两次是两个事件）
                                + dismiss：长按看详情与出牌互斥
  src/input/hitTest.ts          屏幕空间命中（指针在 mesh 外松开也能判定目标）
  src/stage/formation.ts        左右阵营队形（纯函数，0–6 敌，业务 slot 不重编号）
  src/stage/combatLayout.ts     版面唯一来源：相机/扇形/四块区域（纯函数，含安全区）
  src/stage/Stage.tsx           场景、相机适配、扇形、命中面、每帧投影
  src/stage/layout.ts           投影结果（卡牌/敌人的屏幕坐标 + visibleW + hitX）
  src/overlay/TextOverlay.tsx   DOM 文字覆盖层（三档字号、紧凑态）
  src/hud/Hud.tsx               uikit HUD（只有数字与拉丁字母，见 §2.2）
  src/mock/scene.ts             Mock 局面（卡名与规则来自真实内容）
  src/probe.ts                  window.__p1（闸门读语义，不解析 DOM）
```

**一条纪律**：`3D 组件不直接改局面`。所有输入归一化成状态机事件 → `MachineStore` →
唯一的副作用点（`applyCommit`）。P2 把 `applyCommit` 换成 `rd_env_step` 时，Stage 一行都不用改。

## 7. 怎么跑

```bash
# 闸门（不需要 npm，dist 已入库）
node native/ui_next_check.mjs

# 重建（需要网络）
cd web-next && npm ci && npm run build      # 产物进 dist/，闸门读它

# 开发时
cd web-next && npm run dev                  # 打开 http://localhost:5173/?debug
```

`?debug` 暴露 `window.__p1.debug.setEnemyHp(slot, hp)` —— 闸门要造"只剩一个敌人"的局面。
与旧页面 `?debug` 暴露 `givePotion` 同一纪律：**只在查询串里出现 `debug` 时才装**。

## 8. P1 明确**没有**证明的东西

- **真机性能**：headless 软件光栅的 60 fps 什么都不能说明。手机 GPU、触摸延迟、
  低端安卓的 3D 手牌帧率都还没测。
- **uikit 的中文**：HUD 里没有中文（因为默认字体没有中文字形）。如果 P2 要让 uikit 显示中文，
  就得付 §2.2 那笔字体账，或者继续用 DOM 覆盖层。
- **多于 2 个敌人 / 敌人死亡后的目标重排**：Mock 只有两个敌人，槽位稳定性（plan P2 的
  "敌人槽位稳定性"夹具）还没验。
