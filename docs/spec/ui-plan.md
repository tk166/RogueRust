# UI 方案与行动计划（战斗页 / 地图页 / 后续）

> 状态：**方案（未实现）**。这一份是"下一步做什么"的候选与裁决，不是已完成的事实。
> 前置：`web/README.md`（现状）、`docs/spec/run-layer.md` §4.3（地图形状）、
> `docs/spec/sts-act1-plan.md` §4（M0b/M1 的界面判据）。
> **本文里所有"外部项目怎么做的"都带出处；所有"我们还没测"的都标【未验证】。**

## 0. 三句话结论（先看这一节）

1. **渲染技术不用换。** 我们的界面规模是**几十个元素**（手牌 ≤10、敌人 ≤4、地图节点 ≤90），
   而这个规模正落在"SVG/DOM 更合适"的区间里（Konva 的对照表：少量形状 + 需要每个形状都能被
   CSS/事件/无障碍访问 ⇒ 选 SVG）[cite:4acb1818-2]。three.js 的 `three.module.min.js` 单独就是
   **692 KB**（three@0.170.0 的官方构建）[cite:4acb1818-1]，比我们**整个** `.wasm`（382,995 B）
   还大 1.8 倍 —— 为一个卡牌游戏换它，付的是"页面从 0.4 MB 变 1.1 MB"，换不到任何我们缺的东西。
2. **要借的是"结构"，不是"库"。** 最接近的同类项目 *Slay the Web* 的做法值得抄：
   **UI 无关的核心引擎 + 一层的示例 UI**、地图单独一页、`?debug` / `?hand=` 这类 URL 调试开关、
   状态存 URL hash、动画用 gsap 而不是引擎内动画[cite:41374eb9-1]。这些是**纪律**，抄它们不需要加依赖。
3. **真正的欠账是"UI 进不了闸门"。** 现在 `web-package` 只证明了页面**能解析、只在真导出上调用、
   偏移铺得满**；它证明不了任何一个像素是对的。所以第一步（U0）不是画得更好看，而是把
   **渲染函数变成纯函数**（观察向量 → 一个 DOM 描述对象），这样"哪一格显示成什么"可以**被断言**。

## 3. 四个候选，与它们各自的实际代价

| 候选 | 适合什么 | 我们的代价 | 出处 |
|---|---|---|---|
| **DOM + CSS**（现状） | 文本、按钮、列表、网格；可访问、可选中、可 CSS 变换 | 无依赖。动画走 CSS transition / WAAPI。**元素多到几百个**才开始吃紧 | three.js 论坛的官方口吻："屏幕空间 UI 我通常直接用 HTML+CSS，这是最容易也最灵活的做法"[cite:41374eb9-2]；PixiJS 的对照文说 DOM 在约 500 个动画元素处开始掉帧（**厂商博文，未独立复核**）[cite:ff6a0d80-4] |
| **SVG** | **图**（节点+边）、图表、可缩放、每个形状都是 DOM 元素 | 无依赖；节点可直接绑事件、加 `aria-label`、被 CSS 选中 | Konva："需要每个图形元素都参与 DOM（可访问、CSS 选择器、DOM 事件）⇒ SVG；几千个高频变化的形状 ⇒ Canvas"[cite:4acb1818-2] |
| **Canvas 2D**（PixiJS / Konva） | 大量精灵、粒子、逐帧重绘 | 加一个几百 KB 的库；**自己实现命中检测与无障碍**（Konva 明说它不在 canvas 里建可访问元素）[cite:4acb1818-2] | 同上 |
| **WebGL / three.js** | 真 3D 几何、光照、镜头运动、粒子 | `three.module.min.js` = **692 kB**（min，未 gzip）[cite:4acb1818-1]；且**带纹理的文字**要付 `texImage2D` 上传代价 —— three.js 论坛里有人实测：频繁更新的文字用 canvas 纹理，在 Chrome DevTools 里能看到上传开销，而"直接用 HTML 改 `textContent` 更快"[cite:41374eb9-2] | 同左 |

**还有一条反直觉的实测证据**：`arcomage-hd` 是一个"3D 复刻"的卡牌游戏，它的技术栈是
**ts + react + redux + rxjs + CSS-based anim** —— 观感是 3D，动画靠 CSS[cite:73cb6d59-2]。
也就是说"看起来 3D"和"用 WebGL"是两件事。

## 4. 裁决：分层，不是选一个

```
┌─ 结构层：DOM + CSS Grid/Flex ────── 面板、手牌、敌人、日志、按钮   ← 现状已在这一层
├─ 图层：  SVG ───────────────────── 地图（节点 + 边），因为它是图
├─ 观感层：CSS 3D transform + filter  卡面倾斜、翻牌、受击抖动的"纵深"
└─ 动效层：WAAPI（原生）或 gsap       位移/缩放/透明度补间
```

**为什么不是 three.js（把话说透）**：

1. **它解决的问题我们都没有。** 我们是 2D 卡面 + 一个图，没有光照、没有镜头、没有真 3D 几何。
   用 CSS `perspective` + `rotateY` 已经能得到"卡在桌上轻微倾斜"的全部观感。
2. **它的代价是确定的、收益是不确定的。** 692 KB 是**只算库本身**；再算上模型/纹理/加载器，
   页面从 0.4 MB 级跳到 1 MB 级，而我们刚刚为省 76 KB 的数据段换过一次内容镜像
   （`port-plan.md` §45.7）。
3. **它会拆掉我们现有的一条性质。** 现在的页面是"零依赖、零构建、单个静态文件"，
   所以 `web-package` 才能用"逐字节等于重编产物"当判据。引入打包器之后，
   "页面产物从哪来"就多了一层，闸门要重设计。

**什么时候该回头考虑 three.js**（写下来，免得变成永久的"不行"）：需要**真 3D 的战场**
（斜视角、景深、多卡在空间里排队飞出去）或**粒子/后期特效**时。
即便如此，正确做法也是把它做成**可选的观感层**（先跑通 DOM 版，再叠一个 WebGL 画布），
而不是把它当渲染基础。

## 5. 现成的东西里可以直接借的（逐条带出处）

| 借什么 | 出处 | 为什么值得抄 |
|---|---|---|
| **核心与 UI 分层**：核心是"UI 无关的引擎"，UI 是"示例界面" | Slay the Web 的 README 原话[cite:a48b74a8-1] | 我们已经天然是这个结构（内核 / wasm / 页面），但**没有把这条写进任何文档**，所以每次改 UI 都在猜哪些逻辑该放哪 |
| **地图单独一页**（`map-demo.html`，作者自己说"kind of cool"） | Slay the Web 文档[cite:41374eb9-1] | 地图可以独立开发与截图，不被战斗页的状态拖住 |
| **URL 调试开关**：`?debug`（跳过开场、自由走图）、`?hand=A,B`（指定起手）、状态存 hash | Slay the Web 文档[cite:41374eb9-1] | 这条对我们是**最大**的收益：现在要看"某张卡在手里的样子"必须先打到那一局 |
| **动画库用 gsap、声音用 Web Audio** | Slay the Web 文档[cite:41374eb9-1] | gsap 是**可选的动效层**，不侵入结构层；我们也可以先用 WAAPI |
| **开源 UI 素材与图标**：RPGUI、game-icons、oldbookart | Slay the Web 的 References[cite:a48b74a8-1] | 我们是纯文本界面，缺的是**图标**（能量/格挡/意图），不是美术 |
| **开源素材**：`arcomage-hd` 的 CSS 动画方案 | [cite:73cb6d59-2] | 参照它证明"3D 观感 = CSS" |

⚠️ **不要借的**：Slay the Web 的**引擎**。它是 JS 的 StS 实现，与我们的 Rust 内核是**竞争关系**；
抄它的引擎会让"内核可以逐字节对拍 C# 参考实现"这条最贵的资产作废。我们借的是它的 **UI 组织方式**。

## 6. 行动计划（U0–U3，每步一条命令 + 一句证据串）

### U0 —— **让渲染可被测**（先做这个，因为它让后面每一步都有回归保护）

* **做什么**：把 `web/index.html` 的渲染拆成 `render_*` **纯函数**：
  输入 = 观察向量的一个只读快照 + 动作表；输出 = 一个**普通对象**（每格显示什么、哪些按钮可点）。
  再写一层薄薄的"把对象贴到 DOM"。后者留在浏览器里，前者进 Node 测试。
* **为什么是纯函数而不是"用 DOM stub 跑一遍"**：我们要断言的是**语义**（"HP 格显示 67 而不是 80"），
  不是 DOM 的形状；纯函数的测试不依赖任何 DOM 实现，也不会因为换渲染技术而重写。
* **判据**：`node web/ui_test.mjs` ⇒ 退出 0 且输出 `UI_RENDER PASS`；
  并且**成对**：故意把血量格改成读上限 ⇒ **必须红**（这条是 U0 存在的全部理由）。
* **进闸门**：作为闸门 15 `web-ui`，`MustMatch` = `UI_RENDER PASS`。

> **U0 已落地（2026-10-19，当日）。** 形状：`web/ui_render.js`（经典脚本，挂 `globalThis.RD_UI`，
> 零构建、零依赖；放**观测布局常量**与四个纯描述函数 `describeHero/describeEnemies/
> describeHand/describeStatus`），`web/index.html` 只做"把描述对象贴到 DOM"，
> `web/ui_test.mjs` 用真 `.wasm` 驱动描述函数并断言。
>
> ⚠️ **它不覆盖 DOM。** 有一个 bug 就是这一条的直接教训：重构后我把页面里模块级的
> `playOptions` 删掉了，而两个点击处理器还在读它 ⇒ **页面渲染完全正常、15 道闸门全绿、
> 但一次点击都不生效**。Node 测试看不见它（点击处理器是 DOM 那一半，故意不进测试）。
> 是"真浏览器里点一局"发现的（`web/README.md` 的实例化路径那次）。所以 U0 之后，
> **真浏览器仍然是不替代的一步**，这一点写在这里，免得以后有人以为 15 道闸门够了。
>
> **变异结果（9 条，全部真的红）**：
> | # | 变异 | 判红的断言 |
> |---|---|---|
> | M1 | 血量格读 `HP_MAX` | 逐格比对：`hero hp shows 80, the observation says 68` |
> | M2 | 敌人血量格读上限 | 被打的敌人 `still shows 28 HP` |
> | M3 | 意图伤害恒 `null` | 逐格比对：`intent damage shows null, says 7` |
> | M4 | 卡名恒占位 `def#N` | `card 0 has no name` |
> | M5 | 双目标的卡走直打快路 | `card 1 has two targets but would be played directly` |
> | M6 | 页面不再调用 `describe` | `never calls RD_UI.describe()` |
> | M7 | 敌人状态计数恒 0 | `after playing bash: status count shows 0, says 1` |
> | M8 | 敌人恒 `alive` | 战斗结束：`alive shows true, says false` |
> | M9 | 能量格读 `ENERGY_MAX` | `after playing bash: hero energy shows 3, says 1` |
>
> **其中两条（M7、M8/M9）是真缺口，不是测试写错** —— 第一轮扫变异时它们**是绿的**：
> * 敌人状态计数当时只断言"是个数"，一个恒 0 的实现照样过 ⇒ 补了逐格比对 + 一条**非零实例**
>   （打出 `bash` 让 `vuln` 真的挂上，否则"恒 0"和"读对格子"在只见过 0 的测试里无法区分）。
> * 敌人 `alive` 与英雄 `energy` 当时没有任何断言 ⇒ 一个恒 `true`、一个恒读上限，第一次采样
>   都看不出问题（起手与回合开始，能量**恰好**等于上限）⇒ 补了"每次付款之后能量必须低于上限"。
>
> 结论一句话：**"逐格 == 观察向量那一格"这一条才是主力**，前面那些具体断言只是把失败信息
> 说得更清楚。只写具体断言（"血量应该是 68"）会漏掉所有"这次采样恰好相同"的常量。

### U1 —— 地图页（SVG）—— **已落地（2026-10-19）**

> 形状：`web/map_render.js`（经典脚本挂 `RD_MAP`：run 观察布局 + 节点字段 + `describeMap`
> 纯函数 + `svgMarkup` 纯函数 + `statusLine`）、`web/map.html`（只负责贴 DOM 与点处理器）、
> `web/map_test.mjs`、闸门 16 `web-map`。
>
> **它同时是一次 ABI 扩展**（`env-abi.md` §11，先改文档再改代码）：`rd-wasm` 现在依赖
> `rd-run`，并导出 `rd_run_start/seed/observe/map_len/map_rows/map_node/map_row_first/
> action_count/action/action_arg/step/last_error*/kind_name*`。
> `RunState` 的起始数值**从内容读**（新增 `Content::character_start_facts`，
> 读 `Characters[0].Start` 的 `MaxHealth`/`StartingHealth`/`Resources.gold`），不是抄常数。
>
> **6 条变异全部真的红**：行读成列 / 可达集合改成"前 N 个节点" / 出边目标整体 +1 /
> 页面自己编一套 kind 名 / 游标永不标记 / 页面不再调用 `svgMarkup`。
> 其中**两条第一轮是绿的**，原因都是同一个：**"视图与模块对账"只在开局做了一次**，
> 而那两个变异恰好在开局时与真值重合（floor 1 的"前 N 个节点"就是整行；开局还没有游标）。
> ⇒ 修法是把对账写成一个 helper，**走完整张地图的每一步都跑一遍**，并且换第二个 seed 再跑一遍。
>
> **画出来之后才发现的算法问题**：地图会收窄成漏斗（最极端的一层只剩 1 个节点）。
> 先加了一条"优先选未被占用"的 `[推断]` 偏好（平均每行 2.56 → 3.30），随后由用户指出
> **原作不会出现一层只有一个节点**，于是把它升级成一条**规则**（`MIN_NODES_PER_ROW = 3`，
> 太窄的抽样整次作废重来）。最终实测 300 个 seed：失败 0 次、最窄的一层 4 个节点、
> 平均每行 **4.62**。详见 `run-layer.md` §7.3。
>
> 随后又由用户看出**地图是几道彼此孤立的道**（一次"走进这一道就再也到不了那一道"），
> 量下来 60/60 张图不止一个连通块。根因是"优先选未被占用"这条偏好：它把 6 条路径逼成了
> 6 条平行的道，而**共享节点正是岔口的来源**。最终把连接方式整个换成"先定每层节点、
> 再连成共享一个节点的连续段"（`map.rs::connect_rows`，`run-layer.md` §7.4 记了这次规格偏离），
> 60/60 连通、宽度平均 4.53。
>
> ⇒ 这一条值得单独记住：**"画出来"是唯一能发现"合法但形状不对"的手段** —— 而且要看两次：
> 第一次看出"漏斗"，第二次才看出"孤立的道"。
> 13 条规则一条都没违反、闸门全绿，而图是错的 —— 因为"每行最多 6 个"从来不保证"每行不止一个"。
>
> ⚠️ 仍然只有真浏览器能验的那一半：SVG 上的点击处理器。真浏览器实测过：39 节点 / 47 边 →
> 点第一个可走节点 → 游标移动、floor 1、光照集合变成该节点的出边 → 一路点到 floor 15
> （可达 0）。**未做**：`?seed=`/`?debug` 之类的 URL 开关（§5 表里列了，属 U2）。

#### U1 的原始任务书

* **做什么**：一页地图，按 run 层的 `RunMap`（`run-layer.md` §4.3）画 15 行节点与边；
  节点类型用图标/颜色区分，当前位置高亮，可点可达节点。纵向滚动（StS 的地图是自下而上滚的）。
* **依赖**：run 层要能出地图 —— **已具备**（`kernel/rd-run/src/map.rs`，978 行，17 条测试）。
  还缺一条 wasm 侧导出（把地图的节点/边摊成整数数组）。
* **判据**：`node web/map_test.mjs --seed 7` ⇒ `UI_MAP PASS (rows=15, nodes=K, edges=E)`，
  且 K/E 与 `rd-run` 对同一 seed 打印的数字**一致**（跨语言自证，不需要 oracle）。
* ⚠️ 这条判据的形状值得注意：它比的是**我们自己两个实现**的一致性，不是与原作一致 ——
  run 层没有 oracle（`sts-act1-plan.md` §2 G6），所以判据只能这样设计，且必须写明。

### U2 —— 战斗页正式化 —— **动画与日志已落地（2026-10-19）**

> 形状：`ui_render.js` 里加了三层**纯函数** —— `diffObservations`（两步观察向量之差 →
> 事件表）、`logLines`（事件表 → 日志文本，带**阅读顺序**）、`animationPlan`（事件表 →
> "在哪、飘什么、抖谁、塌谁"）。页面只负责把它们画出来。
>
> **为什么动画不直接读引擎事件**：`env-abi.md` §4 每步给两个观察向量、**没有事件流**，
> 所以事件是**相减推出来**的。这覆盖了所有可见量，但有一件事推不出来：格挡的减少
> 是**挡下了伤害**还是**回合结束被清空**。所以调用方要说明这一步是不是结束回合，
> 两种情况**分别报告**，而不是合成一个会错一半的数。真正的引擎事件流更好，已记为欠账。
>
> **判据（9 条变异全部真的红）**：伤害 == 预览值 / 能量 == 卡费 / 格挡增益与回合末清空的
> 区分 / 抽牌数（**不能用抽牌堆的 delta** —— 第一版就是这么错的，报"抽了 0 张"而手牌刚从
> 0 变 5）/ 敌人死亡事件 / 结果事件 / 空操作步骤**不产生任何事件与动画** /
> 日志的阅读顺序（手牌离开 → 消耗 → 伤害）/ 页面确实调用了这三层。
>
> ⚠️ **`appendLog(diff);` 这条字符串检查是变异逼出来的**：删掉页面里的那次调用，
> 上面所有断言依然全绿 —— 因为纯函数全都还在、只是没人用。这是"覆盖不到的地方看起来最绿"
> 的又一例。
>
> **第二部分（同日）：拖拽出牌 + 音效。**
> 交互的第二条路是**拖**，它走**一个决定函数** `RD_UI.actionFor(options, handSlot, targetSlot)`；
> 拖到"这张牌够不到的地方"必须返回 `-1` 并且**什么都不做** —— "替玩家选目标"正是这个页面
> 曾经真出过的 bug。指针管线约 40 行，而"哪些敌人该亮"是 `RD_UI.dropSlots`，也是纯函数。
> 拖完会再触发一次 click，页面**吞掉恰好一次**，否则一次拖拽会打两张牌。
>
> 音效是 `RD_UI.soundPlan(diff) → id 列表`，页面用 Web Audio 的振荡器发一个短促的频率扫过 ——
> **仓库里一个音频文件都没有**。`AudioContext` 在第一次手势时创建（浏览器要求）。
>
> **还没做的**（明确点名，不留暗示）：卡面只有**名字 + 费用**（类型与描述文案不在 ABI 里，
> 需要第二次 ABI 扩展）；**没有动画曲线调优**（时长/缓动是拍出来的，没有对着真机手调）；
> **移动端没有实测**（`touch-action: none` 已加，触摸手势没在真机上试过）；没有遗物/药水的界面。

#### U2 的原始任务书

* 卡面：费用角标、类型条、数值、升级态；手牌扇形/一行两种布局。
* 战斗日志（P3）：内核已经能给出 `FightOutcome` 与 `problems`，需要一条导出把最近 N 条摊出来。
* 动画（P4）：伤害数字、受击抖动、抽牌位移。**动效层不许读内核状态**，只消费"上一步发生了什么"。
* 目标选择（P5）：区分"需要目标/不需要目标"。
* 移动端（P6）：窄屏下手牌横滑、按钮加大。
* **判据**：U0 的那套断言扩到新格子；加一条"日志条数 == 发生的伤害次数"的成对断言。

### U3 —— 观感层（可选，且**站在 CSS 上**）

* CSS `perspective` + `rotateY` 的卡面倾斜、翻牌；`filter` 做受击白闪。
* **明确不做**：three.js。除非出现 §4 末尾那三个条件之一。

## 7. 我认为最可能翻车的地方

1. **把 U0 做成"再写一套 UI"**。U0 的产出是**纯函数**，不是新页面；如果它顺手重写了页面，
   那这一轮就同时改了语义与外观，出了红分不清是谁。
2. **wasm 导出越加越多，闸门 14 的"逐字节同一"变成负担**。现在每次内核改动都要重编+复制一次
   产物（实测：`currentHealth` + 生命周期节目让 `.wasm` 从 378,962 → 382,995 B，闸门先红后绿）。
   UI 需要的新导出（地图、日志）会让这件事更频繁 ⇒ **把"重编 + 复制"写成一个脚本**，
   而不是每次手工记两条命令。
3. **`?hand=` 之类的调试开关变成隐藏 API**。它们必须是**显式**的（写在 README 与页面上），
   否则下一个人会以为"起手牌是内容里写死的"。
4. **地图的判据自证循环**：如果 `map_test.mjs` 的实现与 `rd-run` 的实现都从同一份错误理解出发，
   两边一致但都错。对抗手段只有 `run-layer.md` §7.3 那张 `[推断]` 表 + 人工看图。

## 8. 未验证 / 待实测（不许在别处当成已确认）

1. **three.js 的体积是本页引用的 unpkg 目录列表数字（692 kB，`three.module.min.js`）**；
   没在**我们这个页面**里量过 gzip 后的实际增量，也没做过引入实验。
2. **Slay the Web 的 UI 代码没读过**，只读了它的 `DOCUMENTATION.md` 与 README。
   它的 `src/ui`（web components + preact + htm）具体怎么组织**未验证**。
3. **DOM 在 500 元素处掉帧**是 PixiJS 的博文数字，**单源且带商业动机**，没有独立复核；
   我们的规模（几十个元素）远低于它，所以这条只是"不需要担心"的依据，不是设计依据。
4. **没有量过移动端**：触摸事件、窄屏布局、iOS Safari 的 wasm 加载都还没测过。
4b. **DOM 那一半（模板字符串、CSS、点击处理器）仍然只有真浏览器能验**。U0 之后的已知漏洞
   就是这个形状：一个"页面渲染全对但点击全不生效"的重构，15 道闸门一条都不会红。
5. **地图的纵向滚动在触屏上的手感**（惯性、吸附）没测过。
