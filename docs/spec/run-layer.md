## 0. 三句话结论（先看这一节）

1. **run 层不共用战斗那条单流。** 它用**七条按名字分开的子流**，每条自带计数器；派生函数的
   输入是 `(run_seed, stream_id, counter)`，输出喂给内核已有的 `rng::initial_state/next_u32`。
   这样"多抽了一瓶药水"只推进 `potion` 那条流，**地图一个格子都不会变**。
2. **`run_hash` 不是"把状态序列化"，而是"逐字段固定序的规范文本"**，照 `CombatStateHasher`
   的做法（`SEMANTICS-v1:§6.1`）。判据不是"看起来全"，而是**逐字段扰动测试**：改动任一进哈希的
   字段必须换哈希；每个**不**进哈希的字段必须在 §5.3 里写明"为什么它不影响下一步"。
3. **这些数字都不是原作的数字。** run 层的随机数**没有参考实现可对拍**（`sts-act1-plan.md`
   §2 G6），所以本文的派生函数、流编号、取模方式**全部是我们自己定的**，正文逐处标了
   `[我们的设计]`，任何地方都不许写成"与原作一致"。

## 2. 为什么形状必须现在定（不是"以后再说"）

`sts-act1-plan.md` §5.4 的原话是这条不能后补。具体的坏形状长这样：

```
run_seed = 7, 共用一条流
floor 3 节点是 ? 房 → 抽了 1 次事件 → counter: 41 -> 42
floor 4 地图节点的类型掷点读的是 counter 42 而不是 41
⇒ 玩家在 floor 3 的**任何**随机动作都会改变 floor 4 之后整张地图
```

后果不是"某条测试红"，而是**确定性回归这条判据自己失效**：任何无关操作的差异都会让
`run_hash` 分叉，于是它再也分不清"生成器有 bug"和"你多抽了一瓶药水"。这类判据一旦被
误诊过一次，团队就会开始忽略它的红灯 —— 这比没有判据更糟。

## 3. RNG 形状（**这一节是要签字的部分**）

### 3.1 内核今天有的原语（实测，不是回忆）

| 项 | 位置 | 形状 |
|---|---|---|
| 派生初始状态 | `kernel/rd-core/src/rng.rs:21` | `initial_state(seed: i32, step: i32) -> u32`，公式 `seed ^ step*0x9E3779B9 ^ 0xA5A5A5A5`，零值重映射为 `0x6D2B79F5` |
| 一步输出 | `rng.rs:32` | `next_u32(&mut u32) -> u32`（Mulberry32 变体） |
| 整趟洗牌 | `rng.rs:47` | `shuffle_indexes(out: &mut [u8], seed: i32, step: i32)`，Fisher-Yates 下降循环 |
| 取一个 | `rng.rs:65` | `shuffled_pick_index(count, seed, step)` = 洗完整趟再取 `[0]` |
| 战斗内的消费点 | `state.rs:3737` / `state.rs:3761` | 洗牌用 `(random_seed, random_step)`，洗完 `random_step += 1` |
| 战斗的种子来源 | `battle.rs:168` | `FightPlan::seed: i32`，由调用方给 |

**关键性质**：RNG **无内部状态** —— 一切都从 `(seed, step)` 重新派生（`rng.rs:3-10`）。
⇒ 一条"子流"不需要任何新原语，只需要**一个派生出来的 seed** 和**一本自己的计数器**。

### 3.2 七条子流

| # | 流 | 谁用它 | 为什么单独一条 |
|---:|---|---|---|
| 1 | `Map` | 地图版式、节点类型掷点、`?` 房抽取 | 地图只该被地图操作推进 |
| 2 | `Combat` | 每进一场战斗取一个 `fight_seed` | 战斗内部的洗牌**不许**碰 run 层任何流 |
| 3 | `Reward` | 战斗奖励（金币、3 选 1 卡） | "打赢了几场"与"地图长什么样"无关 |
| 4 | `Event` | `?` 房的事件抽取 | M2b 才用得上，位置先占住 |
| 5 | `Potion` | 药水掉落 | §5.4 点名的那个反例 |
| 6 | `Shop` | 商店货架 | M2b，位置先占住 |
| 7 | `Chest` | 宝箱箱型、遗物池 | 与 `Reward` 分开：宝箱与战斗奖励不该互相推进 |

**流编号从 1 开始，`0` 保留为非法。** 理由是一条防御性质：`RunState` 是个 POD，零初始化
是合法的字节模式；如果 `0` 是一条真流，"一个从没初始化过的 `RunState`"就会**看起来像**
在正常使用 `Map` 流。⇒ `stream_id == 0` 在任何入口都要**响亮失败**（`RunError::BadStream`），
不许当成 `Map`。

### 3.3 派生函数 `[我们的设计]`

```rust
const STREAM_MIX: u32 = 0x5F35_6495;   // 与 initial_state 的 0xA5A5A5A5 域分离

fn stream_seed(run_seed: i32, stream: u8) -> i32 {
    let s = (run_seed as u32)
        ^ (stream as u32).wrapping_mul(0x9E37_79B9)   // 同一个 GOLDEN32
        ^ STREAM_MIX;
    let s = if s == 0 { 0x2545_F491 } else { s };      // 零值重映射，理由同 rng.rs:17
    s as i32
}
```

**为什么复用 `0x9E3779B9`**：它就是 `rng.rs:13` 的 `GOLDEN32`，本文件不许抄第二份数字。
**为什么不直接 `stream_seed = initial_state(run_seed, stream)`**：那样 `Map`（stream 1）与
"某场战斗的第 1 步"在 `(seed, step)` 上会撞成同一个状态；两者用同一个原语但必须是**不同的
点**。域分离常量就是这一层隔离。

### 3.4 一次抽取 = `(seed, counter)`，用完 `counter += 1`

```rust
/// 取一条流的当前 (seed, step)，并把那条流的计数器推进一格。
fn draw(&mut self, stream: RunStream) -> (i32, i32) { … }
```

* 取整数值：`let (s, c) = draw(stream); rng::next_u32(&mut rng::initial_state(s, c)) % n`
  —— 与 `shuffle_indexes` 用的是**同一对原语**，不引入新的混合函数。
* 洗牌：`let (s, c) = draw(stream); rng::shuffle_indexes(buf, s, c)`。
* **推进时机照战斗层的惯例**：**先取后推**（`state.rs:3761` 是"洗完再 +1"，等价）。

⚠️ **`% n` 的取模偏置**：`n = 100` 时偏置的量级是 `2^32 % 100` 落在最后一段，**存在但极小**。
原作是 C# `Random.Next(n)`，它自己也有偏置且算法不同 ⇒ **两边都不是均匀分布**，
所以"平均值"这类统计判据必须带容差（`sts-act1-plan.md` §4 M1 判据 ③）。

### 3.5 战斗 RNG 与 run RNG 的接缝

1. 进战斗那一刻：`fight_seed = draw(Combat)` 的 `seed` 部分。
2. 之后战斗内部**只**用 `(fight_seed, random_step)`，`random_step` 活在 `CombatState` 里
   （`state.rs:2778`），战斗结束就丢。
3. 战斗结束后 run 层**不**读回任何战斗 RNG 状态。

⇒ 直接后果，也是判据：**同一场战斗里多洗一次牌，不影响 run 层任何一条流的计数器。**

### 3.6 冻结判据（五条，缺一条这个冻结就是空的）

**已经落地**（`kernel/rd-run/src/streams.rs`，8 条测试）：

| # | 断言 | 能区分出什么错误实现 |
|---|---|---|
| R1a | 先推 `Potion` 流 100 次，`Map` 流接下来 200 次 `draw` 的 `(seed, step)` 序列**逐项相同** | "共用一个 counter"（§2 的坏形状） |
| R2 | `stream_id` 1..=7 派生出的 seed **两两不等且非零**（64 个 run_seed 采样，含 `i32::MIN/MAX`） | 派生函数漏了 `stream` 这一项 |
| R2b | 七个 `stream_seed(7, …)` 由**字面量**钉死 | "重新验算一遍公式"的测试会随公式一起变绿；这条不会 |
| R3 | `draw` 恰好 `+1`，且返回的是**推进前**的值；未被用到的流不移动 | 推进两次 / 不推进 / 取了推进后的值 |
| R4 | `stream_id == 0`/`8` 被拒；`roll(n=0)` 报错且**不吃掉一次抽取** | "0 当默认流" / "零范围当 0" |

**尚未落地**（缺它，"子流"就只在抽取层被证明，没在地图层被证明）：

| # | 断言 | 落地时机 |
|---|---|---|
| R1b | 推进 `Potion` 流 100 次后，`Map` 流生成的整张地图**逐字节相同** | 地图生成器落地那一轮 |

⚠️ 这五条**都不能**证明"与 StS 一致"—— 因为不存在那个标准。它们证明的是**我们自己的
确定性**。写成"已验证与原作一致"就是撒谎。

## 4. `RunState` 形状

### 4.1 为什么它是一个独立结构，不进 `CombatState`

`CombatState` 是 `Copy` 的 POD、`forbid(unsafe_code)`、零分配，尺寸 213,224 B
（真值在 `state.rs::state_fits_the_sram_plan` 的 println 里）。run 层活得更久（整局），
战斗状态每场重建 —— 塞进同一个结构会让"下一场战斗"必须先把上一场的 213 KB 清掉，
也会让 `CombatState` 的体积上界变成两个不相干的量的和。

⇒ **两个结构，一条接缝**：`build_fight_from_content(state, content, plan, &RunState)`。

### 4.2 字段（形状冻结，数字待实测）

| 字段 | 形状 | 备注 |
|---|---|---|
| `seed: i32` | 标量 | 全局种子，进 `run_hash` |
| `floor: i32` | 标量 | 1..=17（`inv:§7.2`） |
| `health: i32` / `health_max: i32` | 标量 | Ironclad 起始 **80/80**（`inv:§2` 表格，`characters.json hp=80`；**Neow 的 +10% 不在 M1**，见 §4.5） |
| `gold: i32` | 标量 | |
| `deck: [Ident<ID_CAP>; MAX_RUN_DECK]` + `deck_len` | 数组 | **顺序 = 获得顺序**，进 `run_hash` |
| `relics: [Ident<ID_CAP>; MAX_RUN_RELICS]` + `len` | 数组 | M1 只有 Boss 宝箱会写它 |
| `potions: [Ident<ID_CAP>; 3]` + `len` | 数组 | 上限 3（`inv:§9.3`），M1 不产出 |
| `map: RunMap` | 定长 | 见 §4.3 |
| `node: i32` | 当前所在节点（`-1` = 还没出发） | |
| `counters: [i32; 7]` | 七条流的计数器 | 见 §3.2 |
| `unknown_room: [(i32, i32); 3]` | `?` 房三条累计概率的当前值 | `inv:§7.5`，每幕重置 |
| `removed_cards: i32` | 商店删卡次数（M2b 用，先占位） | |

`Ident<ID_CAP>` = `ID_CAP(40) + 1` 字节（`state.rs:153`，长度字节在 `state.rs:458` 一带）。

### 4.3 `RunMap` 形状

`7 列 × 15 行`（`inv:§7.1`），每格一个节点槽，`MAX_MAP_NODES` 按 `7 × 15 = 105` 取。
每个节点：`kind: u8`（8 种，见 §7.2 的类型表）、`out_degree: u8`、`out_edges: [u8; 3]`
（目的行内下标，`1..=3` 条，`inv:§7.1`）、`present: bool`（孤点被裁掉后为 false）。

⇒ 105 × (1 + 1 + 3 + 1) ≈ **630 B**，加 `rows: [u8; 15]`（每行实有几个节点，`≤ 6`）。

### 4.4 体积上界：**tripwire，不是目标**

照这一轮已经定下的方针（`port-plan.md` §45.4 与"不为了省内存动架构"那条裁决）：
`RunState` 只设一条**响亮的上界**，超了就红，理由写在断言旁边。初值取 **8 KiB**：
牌组 `MAX_RUN_DECK = 60` → 60×41 = 2,460 B，遗物 `MAX_RUN_RELICS = 24` → 984 B，
地图 ~700 B，其余几百字节。**实测之后按实测改这个数，并在原地写清"抬界换的是什么"。**
⚠️ 与 `CombatState` 一样：**上界有两处就要一起改**（`RunState` 自身的断言 + 探针 crate）。

⚠️ **`MAX_RUN_DECK = 60` 是容量，不是语义 —— 前提是溢出响亮失败。** StS 的牌组在后期
可以超过 60 张（`inv:§3` 75 张可获取 + 牌组本来就能靠奖励长），所以这里不许"取前 60 张"：
超了必须 `RunError::Capacity`。**这条是本项目已经写死的硬规则**（`port-plan.md` §45.4：
"一个容量常量放大后行为会变 ⇒ 它是语义，不是实现选择"）。同理 `MAX_RUN_RELICS = 24`。
遗物实际上限：`inv:§6` 的 140 件里有 22 件是 Boss 池，一局最多拿十来个 ⇒ 24 是**按需**取的，
不是按预算挤的；真撞上就抬，别截断。

### 4.5 M1 的遗物与 Neow（**两件事必须先说清，否则"起始 HP"就是错的**）

1. **起始遗物 `burning_blood` 有效果，M1 必须实现它。**
   `inv:§2`：`Burning Blood` = "At the end of combat, heal 6 HP"（【多源一致】）。
   它**不是**可选项：不实现它，每一场战斗结束后的 HP 都是错的，而"从出发到 Boss"全程
   都在这条数值上。⇒ M1 实现**唯一一个**遗物效果：战斗胜利后 `health = min(health+6,
   health_max)`，并且它必须进 `run_hash`（它改变 `health`，`health` 本来就在哈希里）。
   ⇒ 因此 §5.3 里"遗物效果状态不进哈希"那一行**只对 M1 之后的遗物成立**，
   M1 这一个的效果直接体现在 `health` 上。
2. **Neow 不在 M1。** 它发生在 floor 1 之前、不属于地图节点（`inv:§2.2`），且它的两个分支
   依赖"上一局有没有打到第一幕 Boss"——M1 没有前作历史。⇒ 起始 HP 就是 **80**。
   **这是一条必须登记的降级**（原作拿 Neow 之后是 88 或带 `Neow's Lament`）：
   登记进 `sts-act1-plan.md` §7 的降级表，写明"何时会被发现" = 开局第一屏的 HP 数字。
   ⚠️ 降级表今天的载体还是文档（`native/sts_deviations.json` 尚未建）；在它建起来之前，
   **这一条写在文档里也是有效的登记**，但 M1 落地时必须有人去建那个文件，否则"降级表 +
   闸门"这条机械手段就还是空的。

## 4.6 遗物（2026-10-19 加）

### 4.6.1 形状：`REL` 行 + `Start.StartingRelics`

`REL` 表在格式里一直存在（stride 12：`Id` / `DisplayName` / `RunPrograms` / `CombatRules` /
`extra`），内容里一直是 **0 行**。现在有了第一行 `burning_blood`，并挂到
`Characters[0].Start.StartingRelics`（`Start.StartingRelics` 是同一份的第二副本，闸门要求两者一致）。

`Content::start_relics(roots)` 的两跳规则与 `start_deck` **逐字相同**（花名册非空看
`Characters[0].Start`，否则看根 `Start`）；返回 `Ok(None)` = 没声明，不是错误。

### 4.6.2 效果**不是**数据 —— 这是一条必须说清的边界

`REL.RunPrograms` / `REL.CombatRules` **本内核一行都不执行**：没有 run 层的节目解释器，
也没有 `CombatRules` 注册表（这份内容里 23/23 状态都是 ABSENT，所以那个注册表从来没建过）。

⇒ 效果是**按 id 逐条实现的规则**，住在 `RunState::end_of_combat`。已实现：

| 遗物 | 效果 | 依据 |
|---|---|---|
| `burning_blood` | 战斗结束回 6 HP（**上限封顶**，`heal_after_combat` 就是那个原语） | `inv:§2` |

**而且这个边界是响亮的**，两道闸：

1. **内容侧**：`rd_run_start` 读遗物时，若该行声明了 `RunPrograms` 或 `CombatRules`（非空），
   **拒绝开局**并说明原因 —— 收下再来个静默不做，正是这个项目反复踩的坑。
2. **状态侧**：`end_of_combat` 遇到没有规则的 id 返回 `RunError::UnsupportedRelic { index }`，
   **不是空操作**。有一条测试专门用一个"真 StS 遗物但没实现"的 id（`vajra`）钉住它。

### 4.6.3 还没接上的那一跳

`end_of_combat` **今天没有被 wasm 调用** —— 因为 run 层与战斗层之间**还没有结算**
（`run-layer.md` §6 的 `RunAction` 全表、`env-abi.md` §11.5 的"只走不结算"）。
效果本身有单测（`burning_blood_heals_six_at_the_end_of_a_fight`），缺的是**调用点**；
节点结算落地时，那一步就是它的第一个调用者。**写在这里，而不是让"遗物有了"看起来像"遗物能用了"。**

### 4.6.4 `DisplayName` 只在完整镜像里

`DisplayName` 在编译器的 `PRESENTATION_KEYS`（`compile.py:688`）里 ⇒ **core 镜像会把它剥掉**。
这与卡面文案（§57）是同一个机制：页面要显示名字，就得嵌完整镜像。`rd-wasm` 现在嵌的就是完整镜像。

## 4.7 节点结算与商店（2026-10-19 加）

### 4.7.1 "走"与"结算"是两件事，分开是对的

`enter_node` 只**走**（移游标、走 floor），这一点没有改 —— 那是地图页整天在做的事，
而且闸门 16 靠"走完整张图"验证连通性。结算由**新的入口**声明：

```rust
begin_node(card_pool, relic_pool) -> Result<NodeKind>   // 这个节点在等什么
```

| 节点 | `begin_node` 之后 | 动作 |
|---|---|---|
| `Combat` | `Pending::None` | 战斗是调用方的事（它跑战斗会话，结束时调 `end_of_combat`） |
| `Rest` | `Pending::Rest` | `rest()`（回 30% 上限）或 `smith(card, upgraded_id)` |
| `Treasure` | `Pending::Chest` | `open_chest(relic_pool)` |
| `Shop` | `Pending::Shop` | `buy_card` / `buy_relic` / `remove_card` / `leave` |
| `Elite` / `Unknown` | **错误** `NodeNotSettleable(kind)` | M1 不做，响亮拒绝 |

`Pending` 是一个相位机：**在错相位调动作一律 `WrongPhase`**，不是空操作。这条很重要 ——
"在篝火里买东西"如果能成功，那张地图就不是一个状态机了。

### 4.7.2 商店：内容侧提供**池**，run 层只挑与定价

`rd-run` **不认识内容**（模块头写死了这条），所以商店的候选由调用方给：
`begin_node(&card_pool, &relic_pool)`。挑选用 `Shop` 子流（洗牌），定价用 `Shop` 子流掷点。

* 卡价 **45–55**、遗物价 **143–157**；删卡 **75**，此后每删一张 **+25**（`inv:§8.2`）。
* ⚠️ **`[推断]`：价格按"全部 Common"取。** `inv:§8.2` 的价格区间是**按稀有度**分的，
  而这份内容**没有稀有度字段**（`CARD` 行里没有 `Rarity`）⇒ 抄一个稀有度就是编一个事实。
  等内容有了稀有度，价格表才谈得上"与原作一致"。
* 宝箱完全照 `inv:§8.3`：箱型 50/33/17，出金概率 50/35/50，金额 23–27 / 45–55 / 68–82。

### 4.7.3 删卡：价格会涨，而且**跨店累计**

`remove_card_price() = 75 + 25 × removed_cards`（`removed_cards` 这个字段本来就在，
之前只是"占位"）。删卡要保持**牌组顺序**（顺序可观察，`run_hash` 会逐张写出来）。

### 4.7.4 这一轮没做的（说清，别让"能结算"看起来像"能玩"）

* **没有 ABI，也没有界面**：`begin_node` / `rest` / `shop` / `chest` 目前**只有 Rust 测试**在调。
  地图页仍然只"走"。下一步是把这套动作摊成 `env-abi.md` §11 的动作（`RunAction` 那六个），
  再给地图页一个"节点面板"。
* **战斗结算没有接**：`Combat` 只把 `Pending` 置空；奖励（金币、3 选 1）与 `end_of_combat`
  的调用点都还没有。
* **Smith 的 `+` 映射是调用方给的**（`smith(card, "strike+")`）：这份内容里升级是**另一张 CARD 行**，
  而"哪一行是它的升级版"是内容的约定，不是内核该猜的后缀 —— 所以内核不猜。

## 5. `run_hash` 规范文本

### 5.1 为什么需要它（而不是"比较两个结构体"）

`sts-act1-plan.md` §5.3 V1：只比"终局地图相同/奖励相同"证明力太弱 ——
"奖励取整错一位但每次错得一样"会全绿。照 `CombatStateHasher` 的做法产出一段**规范文本**，
逐步比较，才能把"哪一步开始分叉"变成可定位的事实。

### 5.2 文本形状（`[我们的设计]`，冻结）

```
run v1\n
seed <i32>\n
floor <i32>\n
health <cur>/<max>\n
gold <i32>\n
removed <i32>\n
deck <count>\n
  <definition_id>\n            × count（**获得顺序**，不排序）
relics <count>\n
  <relic_id>\n                 × count（**获得顺序**）
potions <count>\n
  <potion_id>\n                × count（**槽位顺序**，含空槽？见 5.3-4）
map <node_count>\n
  <row> <col> <kind> <out_degree> <e0> <e1> <e2>\n   × 每个 present 节点，(row, col) 升序
node <i32>\n
unknown <a>/<b>/<c>\n
rng <stream> <counter>\n        × 7，按 stream id 升序
```

* 分隔符一律单个空格，行尾 `\n`（LF，不是 CRLF），**没有**尾随空格，末行也以 `\n` 结尾。
  （`SEMANTICS-v1:§6.1` 的规范文本也是这个约定；不这样，`fc /b` 在不同机器上会假红。）
* 数字一律十进制、无前导零、负数带 `-`。
* 集合型字段**逐处写明排序规则**：`deck`/`relics` 是"获得顺序"（顺序可观察 ⇒ 必须进哈希，
  且**不能**排序），`map` 是 `(row, col)` 升序（顺序不可观察）。

### 5.3 什么**不**进哈希，以及为什么（逐条，不许省）

| 不进 | 为什么不影响下一步 | 什么内容一来它就不成立 |
|---|---|---|
| 战斗内部的 `CombatState`（牌区、能量、格子） | 它每场重建，且已由 `FIGHT_DIFF` 的四层对拍管着 | 若将来"跨战斗保留手牌"（本作没有） |
| 已走过的节点历史 | 下一步只依赖当前节点与各流计数器 | 若引入"本局去过几次商店"这类累计量（`inv:§7.4` 只有相邻约束，不需要） |
| 遗物**效果**的实现状态（M1 没有效果） | M1 的遗物只有 id | **Boss 遗物一有效果就必须进哈希** —— 现在就写在这里 |
| `problems`（诊断文本） | 它是观测，不是状态（`battle-loop-hooks` 的"问题是观测不是失败"） | 若某个恢复逻辑读它 |

### 5.4 判据：**逐字段扰动**

对 §4.2 的**每一个**进哈希的字段，构造"只改这一个字段"的两份状态，断言哈希**不同**。
再对 §5.3 的每一行构造"只改那一个东西"的两份状态，断言哈希**相同**（否则说明它其实进了）。

⚠️ 逐字段扰动**证明不了**"哈希覆盖了全部"—— 它只证明"进哈希的每个字段都真的进了"。
所以 §5.3 那张表是**判据的一部分**，不是注释：漏写一行 = 一个不知道要不要进哈希的字段。

## 6. 步骤模型

### 6.1 一步 = 一个动作

```rust
pub enum RunAction {
    EnterNode,        // 从当前节点选一条出边进入下一个（M1 只允许"最左/第一条"）
    ChooseCard { index: u8 },     // 奖励 3 选 1（或跳过，见 6.2）
    SkipReward,
    RestSite { option: RestOption },   // Rest 30% / Smith
    OpenChest,
    TakeBossRelic { index: u8 },       // Boss 宝箱 3 选 1
}
```

`step(state, content, action) -> Result<RunStepOutcome, RunError>`：
**纯整数、无分配、无隐藏状态**，与内核的其余部分同一套纪律。

### 6.2 每步之后**必须**成立的不变量（每条都要有测试）

1. `floor` 单调不减，且 `0 < floor <= 17`。
2. `health <= health_max`，`health >= 0`；`health == 0` ⇒ `RunResult::Dead`。
3. 节点类型与 `floor` 的固定层规则一致（`floor==1` 全战斗、`9` 全宝箱、`15` 全篝火、
   `16` 唯一 Boss、`17` Boss 宝箱 —— `inv:§7.2`）。
4. 每个 `EnterNode` 花掉的那条出边必须真的在这个节点的 `out_edges` 里（不许"按编号猜"）。
5. 一次 `RestSite` 只能生效一项（`inv:§8.1`）。
6. 任何"这个动作现在不合法"都必须**响亮失败**（`RunError`），不许静默当成跳过。

### 6.3 `?` 房在 M1 是**有内容的空**

`sts-act1-plan.md` §4.0 R2 的裁决：`?` 房在 M1 **必须**在地图上显示"（未实现）"、

**照样要实现并测试**，只是三条分支里有两条（战斗/宝箱）在 M1 走不通 ⇒ 走不通就**响亮失败**，
不许"退回事件"。

### 7.3 算法（**这一段是 `[推断]`，不是 wiki 原文**）

> ⚠️ 上面这段描述的是**第一版**（走 6 条路径）。它已经被 §7.4 换掉了，保留在这里是因为
> 它记录了"为什么单看规则发现不了漏斗" —— 13 条规则全绿，而图是几道平行的墙。

wiki 给的是**约束**（§7.1 的 13 条），没给过程。我们按约束反推一个过程：

1. **铺格子**：每行 `count = 6`（第 1 行 = 6，其余行也是 6，`inv:§7.1` 的"每行最多 6 个"），
   列下标在行内均匀取 `0..6`，第 1 行固定 `0..5`。
2. **画 6 条路径**：第 `i` 条从第 0 行的列 `start_i` 出发（`start_0 != start_1`，规则 3）。
   每一步在下一行的**最近 3 个**节点里选一个（按列差的绝对值，同距取列小者），
   并把边加进当前节点（`out_degree <= 3`）。
3. **不交叉**：第 `i` 条路径的列序列必须**单调非减**且与第 `i-1` 条在每一行满足
   `col_i >= col_{i-1}`（规则 5）。违反就不接受这次抽样。
4. **孤点**：没有被任何路径走过的节点 `present = false`（规则 6）。
5. **掷点**：逐行、逐节点按 53/8/12/5/22 掷 `kind`，然后套 9–12 四条覆写，
   违规**重掷该节点**（规则 13）。重掷上限 `MAX_REROLLS = 64`，超了**响亮失败**
   （`RunError::MapGeneration`）而不是放宽约束 —— 放宽是最坏的静默。

⚠️ 第 2 步的"最近 3 个"与第 3 步的"单调非减"是**我们的读法**。原作的实现细节
（是否允许同列、如何打破平局、路径的抽样顺序）**没有来源** ⇒ 全部标 `[推断]`，
并在 §8 的分布闸门里用**区间**而不是等式。

**规则 1b：每行至少 3 个节点（2026-10-19 加，来源是用户的领域知识，不是 `inv`）**。
`inv:§7.1` 只写了上界（每行 ≤ 6），而实测出来的地图会**收窄成漏斗**：最极端的一层只剩
**1 个节点**。用户指出**原作不会出现一层只有一个节点** —— 而"一层只有一个节点"等于"这一层
只有一个选择"，那已经不是同一张地图了。所以它是一条**规则**，由
`kernel/rd-run/src/map.rs` 的 `MIN_NODES_PER_ROW = 3` 承载，由 `check()` 的
`MapViolation::TooNarrow` 校验。

**实现方式是"拒绝 + 重试"，不是"修补"**：先生成、再裁孤点、若任何一层窄于 3 就**整次作废重来**
（`MAX_ATTEMPTS = 64`）。这与"违规就重掷"（规则 13）是同一种手法，而且比"事后补节点"诚实 ——
补出来的节点与路径没有关系。

**实测（seed 1..=300，2026-10-19）**：生成**失败 0 次**；最窄的一层 **4** 个节点；
平均每行 **4.62** 个。（加这条规则之前：平均 2.56，13/20 张图有单节点层。）
⇒ `Map` 流的抽取次数**涨了**（seed 7: 128 → **148**），因为被作废的那几次尝试**不会退回**
已经消费掉的抽取。`rd-wasm/src/run.rs` 里钉着这个数。

⚠️ **一条走过弯路要记下来**：先试过"**先决定每行几个节点、再让六条路径覆盖它们**"，
结果**一次都生成不出来**。原因是"最近 3 个、且不能走到上一条路径左边的列"这两条一起用，
在随机撒点的行上经常**一个合法目标都没有**。让走法决定每行长什么样、再把太窄的那次作废，
既简单又可行。

**早先的实测补记（同一个问题的前一半）**：上面的走法会让六条路径**合并**。
路径在"不能往左"的约束下会挤到一起，于是一行里大部分节点**没有路径经过** ⇒ 被"裁孤点"
删掉 ⇒ 地图收窄成漏斗。测量（20 个 seed）：平均每行 **2.56** 个节点，**13/20** 张图至少
有一行只剩 1 个节点。

处置：在走法里加一条 `[推断]` 的**偏好** —— 在"最近 3 个"里**优先选还没有被本行前面的路径
占用的那个**（若都没有，退回原有的随机）。它仍然是"最近 3 个之一"，列仍然单调 ⇒ **13 条
规则一条都没变**，变的只是"在同样合法的选择里挑哪个"。效果：平均每行 **3.30**，只有
**5/20** 张图有单节点行。`kernel/rd-run/src/map.rs` 的
`the_map_is_wide_rather_than_a_funnel` 盯着这个数（门槛 3.0，低于实测值所以不会抖，
高于旧值所以删掉那条偏好就会红）。

⇒ **`Map` 流的抽取值因此变了**：seed 7 的地图生成从 141 次抽取变成 **128** 次
（`rd-wasm/src/run.rs` 里钉着这个数，它变红就是这条偏好被改动的信号）。

⚠️ **个别 seed 仍会收窄**：上面是 20 个 seed 的平均。seed 7 自己就是较窄的一张
（36 个节点 / 每行 2.40 / 有两行只剩 1 个节点）。这是"平均"与"单张"的区别，不是矛盾；
要更宽就得改"不交叉"的读法，而那一条是 `inv:§7.1` 的规则，不是我们的偏好。

### 7.4 连接方式改过一次，而且**是一次有记录的规格偏离**（2026-10-19）

`inv:§7.1` 说地图是**走 6 条路径**生成的：每条路径从第 1 层出发，每一步走到下一层"最近的 3 个"
节点之一。第一版就是这么实现的。它**做不到**同时满足两条性质：

| 性质 | 为什么它是必需的 |
|---|---|
| 每层至少 3 个节点 | 规则 1b，见上：一层一个节点就是一层的唯一选择 |
| 整张图是**一个连通块** | 否则"地图"其实是几张并排的地图：走进 A 道就再也到不了 B 道 |

**实测（320 次抽样，`measure_rejected_draws`）**：为了宽度而把路径推开 ⇒ 6 条**平行的道**
（60/60 张图不止一个连通块；seed 7 是 15/15/24/15）；为了让它们合并 ⇒ 一层只剩一两个节点。
**两者同时成立的抽样是 0/320。**

⇒ 换成"**先定每层的节点，再连接相邻两层**"：每个源节点拿到下一行的**一段连续列区间**，
区间按节点顺序排列，**相邻两段共享一个节点**。共享就是全部机关 —— 它既是连通性
（共享节点把两个源连起来，逐段串成一条链），又是岔口（共享节点有两条入边，下一步就可能
有两条出边）。

**保住的**：出边 1–3（区间长度）、目的地都在源节点的区间内、**不交叉**（区间单调）、
**没有孤点**（区间与共享覆盖每个节点）、每层宽度、**连通**。
**改掉的**：目的地不再是"最近的 3 个"，而是"一段连续的列邻域"（规则 4b）；
地图也不再是"走 6 条路径"走出来的（规则 5b）—— 现在"有多少条路线"是**结果**而不是输入。
两条都写在 §7.1 的表里，标着"我们改了"，不去假装它们还是 wiki 那条。

实现：`kernel/rd-run/src/map.rs::connect_rows`，`[推断]`的贪心切分
（`ceil(剩余目标 / 剩余源)` 再被出边上界和"给后面的源留够"夹住）。
换一个切分方式会得到另一张同样合法的图；选这个是因为它对 `MIN..=MAX` 的**任意**宽度组合都
有解，而且短到能读完。

验收实测：60 个 seed **连通块数全部为 1**、每个节点都能从第 1 层向上走到；
200 个 seed 的 `check()` 全绿（含连通性）；宽度平均 4.53。

## 10. 实现补充（2026-11-03）：脱战与无色牌

### 10.1 脱战是**运行层**结局，不是第四种 `CombatResult`

Smoke Bomb（§179）落地时把"逃出非 Boss 战斗"表达成 `FightOutcome` 的 `result = 3`：
不跑 `end_of_combat`（遗物不触发）、不掷奖励、不给 Boss 记账，但节点**算用掉**（`mark_resolved`）。

为什么不动内核：`CombatState.result` 的三种值与参考**逐字节**一致，而且 `result=` 在
`hash_golden` 的规范文本里 —— 加第四种会动整个 85 份语料。Boss 战拒绝脱战（wiki: non-boss combat）。

### 10.2 无色牌不进任何牌组

滤网在 `full_pool`（**商人**与**奖励屏**都从它取样），不是在 `reward_pool`。这条位置是被数据逼出来的：
只滤奖励池时，三张无色牌会出现在**商店**，驱动器买了它们、牌组变弱、24 个种子里 11 个死得更早
（§185）。一个规则一个出处。

三张无色牌**没有 `+` 行**：不是"不能升级"（StS 里能），而是**没有任何牌组装得下它们**
（唯一入口是 Colorless Potion，在一次战斗内给），`+` 行会是没人能到达的内容。

## 11. 实现补充（2026-11-03）：一次事件选择可以有多条效果

`resolve_event_effects(&[(EventEffect, Option<&str>)], pool)` 取代了单条版本，三条性质：

1. **原子**：任何一条失败 ⇒ `*self = before`（`RunState: Copy` 就是为这个存在的），
   所以"拒绝 ⇒ 一个字节都不改"对**列表**也成立（判据 `a_failing_effect_rolls_the_whole_list_back`）；
2. **最多一条改牌效果**：`remove_card` / `upgrade_card` / `transform_card` 变成一个待答问题，
   而待答只有一个位置 ⇒ 两条报 `TwoDeckChanges`，不静默丢一条；
3. **收尾只有一次**：没有改牌效果时就地收尾（`Pending::None` + `mark_resolved`）。

A15 的选择**不在这里**：运行层只拿到一串已经选好的效果。选哪一串由 `Content::EventChoice::effects_at`
按 `RunState::ascension()` 决定（阈值常量 `A_EVENTS_WORSE = 15`，与其它 `A_*` 摆在一起）。
